# ProgrammingAI 要件定義書

作成日: 2026-08-05
再整理日: 2026-08-24
状態: 現行構成に合わせて再整理

この文書は、ProgrammingAIが満たすべき要件を定義する。
実装手順、検証コマンド、保守時の確認順序は `docs/MAINTAINER_GUIDE.md` に分ける。

## 1. 課題意識

ProgrammingAIの出発点は、プログラミング学習において、自分の勉強を継続的に観察してくれるメンターが欲しいという課題意識である。

AI時代の学習では、分からないことをAIに聞けば、答えやコード例を得ることはできる。
しかし、プログラミング学習で本当に必要なのは、答えそのものだけではない。
自分がどこで多くつまずいているのか、どのような失敗を繰り返しているのか、質問が「答えだけを求める形」に偏っていないかを継続的に観察することが重要である。

自分の学習の特徴は、学習している本人ほど見えにくい。
その場では理解できたように感じても、同じ種類のエラー、同じ構造理解のつまずき、同じ確認不足を繰り返している可能性がある。
また、AIに質問して答えを得ることが簡単になるほど、自分で原因を切り分ける力や、処理を順番に追う力が育っているかを確認しづらくなる。

そのため、ProgrammingAIには、学習者の質問や学習ログをもとに、学習の傾向、つまずきやすい箇所、繰り返し出ている失敗、質問の仕方の癖を観察し、次の学習に向けたアドバイスを返す役割が必要である。
このAgentは、単に答えを返す存在ではなく、学習に伴走し、学習者が自分の理解の状態を把握できるようにするメンターとして設計する。

このAgentの価値は、次の3つにある。

1. 質問を分類し、質問に合った説明の型へ流すこと。
2. 学習ログを通じて、単発の質問を復習できる知識へ変えること。
3. mentor Agentがログから苦手傾向を見つけ、次の学習前に短く助言すること。

## 2. 目的

ProgrammingAIは、Codex上で動くローカルフォルダ型のプログラミング学習支援Agentである。
答えだけを渡すのではなく、考え方、処理の流れ、確認順序、他でも使える見方を中心に説明する。
学習者の質問、理解確認、Learning Case、確定学習ログ、日次学習傾向、learner-profileを通じて、学習者の苦手傾向を見つけ、復習と改善提案につなげる。

目的は、学習者が次の状態へ近づくことである。

- コードやエラーを、答えではなく確認順序で理解できる。
- 複数ファイルの役割と処理の流れを自分で追える。
- 分からなかった内容を学習ログとして残し、あとで復習できる。
- 繰り返し出る苦手を把握し、次の質問時に意識できる。
- Agentの判断基準を日本語で確認し、必要に応じて運用修正できる。

## 3. 基本方針

- 通常の学習者向け会話では、内部検証、保守手順、実装言語の詳細を出さない。
- 学習者には、Codex上で質問すれば使えるAgentとして振る舞う。
- 回答は日本語を基本にする。
- 最初は、考え方、全体像、確認順序を優先する。
- 修正案やコード例は、理解に必要な場合だけ出す。
- 各回答の最後に、軽い理解確認を1つ入れる。
- 学習者が明示した範囲だけを参照する。
- 承認なしに確定学習ログを保存しない。
- サブAgentは直接ファイルを更新せず、main Agentへ更新案を返す。
- 学習ログやmentor分析はProject内だけに保存する。

## 4. 利用対象

対象にする入力は次の通りである。

- プログラミング学習に関する質問
- チャットに貼られたコード、エラー文、説明、設計、テスト内容
- 学習者が明示したファイル、ディレクトリ、行番号、関数名、画面名
- 学習ログ化、復習、学習開始などのProgrammingAI運用入力

対象外にするものは次の通りである。

- 学習者が明示していないファイルや周辺コードの自動探索
- 秘密情報、認証情報、不要な個人情報の参照
- 外部サービスへの自動保存
- 学習者の承認なしでの確定学習ログ保存
- 学習ログ保存先としてのCodex全体メモリ利用

## 5. Agent構成

ProgrammingAIは、main Agent、回答系Skill、共通制御Skill、mentor Agentで構成する。

main Agentの責任は次の通りである。

- 設定状態を確認する。
- 参照範囲を確認する。
- 質問分類を行う。
- 分類に応じた回答Skillを使う。
- プログラミング学習質問をLearning Caseへ一次記録する。
- ログ化確認、ログ候補、保存許可、確定保存を管理する。
- 日次学習傾向、mentor-briefings、learner-profile、mentor MEMORYの更新候補を扱う。
- ファイルへ反映する前に、必要な確認を行う。

回答系Skillは次の通りである。

| Skill | 役割 |
| --- | --- |
| classifier | 質問分類、分類理由、確信度、不足情報、回答前確認の要否を返す |
| feature-answer | 機能全体、複数ファイル、処理とデータの流れを説明する |
| unit-answer | コード一文、関数、メソッド、API、構文を分解して説明する |
| assess-answer | 学習者のコード、設計、説明、テスト、理解内容を評価する |
| error-answer | エラー内容、原因仮説、確認順序、修正案、検証方法を整理する |

共通制御Skillは次の通りである。

| Skill | 役割 |
| --- | --- |
| config-defaults-provider | configの初期値と復旧テンプレートを返す |
| config-guard | configの必須key、型、許可値、範囲を確認する |
| scope-reader | 明示された参照範囲だけを見るように制御する |
| learning-log-workflow | Learning Case一次記録、ログ候補、保存許可、確定ログ、軽量メモを管理する |
| profile-memory | 日次傾向、learner-profile、苦手候補を管理する |

mentorだけは、独立Agentとして `.codex/agents/mentor/` に置く。
mentor Agentは分析を行うが、保存権限はmain Agentに残す。

日次処理は、UserPromptSubmit hookから呼ばれる `.codex/internal/scripts/daily_rollup_on_prompt.rb` が行う。
このscriptは、当日のmentor-briefingsがある場合は何もせず終了し、ない場合だけ前日のLearning Caseから日次学習傾向と当日のmentor-briefingsを作成する。

## 6. 質問分類要件

質問分類は、次の4つに固定する。

```md
feature
unit
assess
error
```

`summary` は明示的な要約依頼やログ化契機として扱い、質問分類にはしない。
`test` はテストコードや技術領域の文脈として扱い、質問分類にはしない。

分類基準は次の通りである。

| 分類 | 判断基準 |
| --- | --- |
| feature | 複数ファイル、機能全体、処理やデータの流れが中心 |
| unit | コード一文、関数、メソッド、API、構文の意味が中心 |
| assess | 正しいか、十分か、問題ないか、評価してほしい内容が中心 |
| error | エラー、例外、失敗、動かない、テスト失敗の切り分けが中心 |

複数に当てはまる場合は、学習者が最初に解決すべき問題を優先する。
エラー文が提示されている場合は、全体相談に見えても原則として `error` を優先する。
学習者の理解内容を評価する依頼が中心の場合は `assess` を優先する。

分類結果には、分類、分類理由、確信度、不足情報、回答前確認の要否を含める。
学習者向けには、分類と分類理由だけを短く表示する。

## 7. 回答要件

回答は、分類ごとに型を分ける。

feature回答では、次を重視する。

- 関係するファイルやコードの役割
- 入力またはユーザー操作の起点
- 処理が渡る順番
- データが作られる場所、渡される場所、使われる場所
- 画面表示、DB保存、API応答などの終点
- 次に同じ問題が出たときに見る順番

unit回答では、次を重視する。

- 対象コードを小さな部品へ分解する。
- 左側の値、呼び出すメソッド、引数、戻り値、副作用を分ける。
- 実行順序を説明する。
- 他のコードを読むときにも使える見方へつなげる。

assess回答では、次を重視する。

- 合っている部分と不足している部分を分ける。
- 正誤だけで終わらせず、改善案と次の確認順序を出す。
- 学習者の現在の理解段階を否定せず、次に直す一点を明確にする。

error回答では、次を重視する。

- エラーの意味を説明する。
- 発生場所と分かっている事実を分ける。
- 原因を断定せず、可能性の高い順に仮説を出す。
- 修正案より先に確認順序を示す。
- 修正後の検証方法を出す。

すべての回答で、最後に軽い理解確認を1つ出す。

## 8. 参照範囲要件

ProgrammingAIは、学習者が明示した範囲だけを参照する。

参照してよいものは次の通りである。

- チャットに貼られた内容
- 明示されたファイル
- 明示されたディレクトリの許可範囲内一覧
- 明示された行番号、関数名、画面名、エラー発生箇所

参照範囲が曖昧な場合は、候補を提示して確認する。
候補先の中身を先に読まない。

秘密情報の可能性がある内容は表示しない。
`.env`、秘密鍵、API key、token、password、認証情報、不要な個人情報は、学習目的に見えても扱いを止める。

参照範囲の広さはconfigで切り替えない。
ProgrammingAIは常に、学習者が明示した範囲だけを参照する。
明示されたディレクトリの一覧確認の深さだけ、`.codex/config.toml` の `scope_listing_max_depth` で扱う。

## 9. Learning Case一次記録要件

Learning Caseは、日付ごとのプログラミング学習質問と、その回答要点、理解確認、ログ化状態、苦手判定に使う一次観察を残す記録である。

main Agentは、会話途中の専用状態ファイルを作らず、入力を受け取ったら次を判断する。

- プログラミング学習質問か。
- 直前の学習質問への追質問または理解確認への返答か。
- 学習開始、ログ保存、設定変更、設計相談などの管理操作か。
- 参照範囲が足りているか。
- 分類が `feature / unit / assess / error` のいずれかに決まるか。

Learning Caseへ一次記録する入力は次の通りである。

- プログラミング学習質問。
- 直前の学習質問に対する理解確認への返答。
- ログ化しない判断をしたが、質問分類やつまずきの観察として残す価値がある内容。
- 参照範囲が不足していて回答に入れなかったプログラミング学習質問の状態更新。

Learning Caseへ記録しない、または状態更新だけに留める入力は次の通りである。

- 雑談。
- 設定変更だけの依頼。
- `学習開始` などmentor起動だけの入力。
- ログ化、保存許可、修正完了などの管理返答。
- ProgrammingAI自体の設計相談。

新しい学習質問へ移る場合、main Agentは前の学習内容を勝手に確定ログ化しない。
復習価値がある場合だけ、ログ化するかどうかを確認する。

## 10. ログ保存要件

プログラミング学習の質問は、ログ化可否にかかわらず `learning-cases/YYYY-MM-DD.md` に一次記録として保存する。
Learning Caseには、質問、つまずき、学習内容を残したうえで、苦手検出の一次観察として次を残す。

```md
苦手種類候補
観察パターン
関連技術語
```

`苦手種類候補` は `技術知識`、`構造理解`、`思考プロセス` のいずれかで記録する。
`観察パターン` は、学習者が何にどうつまずいたかを日本語で具体的に残す。
`関連技術語` は、Laravel、Route、Controller、Blade、Collection、API名、構文名などの補助タグとして扱う。
関連技術語だけで苦手を断定しない。

確定学習ログは、学習者が保存を許可した場合だけ `learning-logs/YYYY-MM-DD-NNN-topic.md` に保存する。

ログ化の基本フローは次の通りである。

```md
Learning Caseへの一次記録
-> 回答と理解確認
-> 必要な場合だけログ化する/ログ化しないの確認
-> ログ候補の作成
-> 学習者による確認または修正
-> 保存する/保存しないの確認
-> 保存する場合だけ確定ログ化
```

`内容をまとめてほしい` は、ログ候補作成の契機として扱う。
ただし、ログ候補を作っただけでは確定保存しない。

学習者が保存しないと答えた場合、確定学習ログと軽量メモを保存しない。
Agent判断による軽量メモは、繰り返しのつまずきや重要な未解決事項に限定する。

確定学習ログは、復習とmentor分析に使える粒度で書く。
会話全文や不要なコード全文を保存しない。

## 11. 保存先要件

ProgrammingAIの学習データ保存先は、このProject内に限定する。

```md
learning-cases/
learning-logs/
notebook/
.codex/agents/mentor/MEMORY.md
```

次の場所は、ProgrammingAIの学習ログ保存先として使わない。

```md
/Users/taiga/.codex/memories/
.codex/memories/
extensions/ad_hoc/notes/
```

`notion-drafts/` は現行構成では使用しない。
外部サービスへの自動保存もしない。

## 12. mentor要件

mentor Agentは、学習ログ、Learning Case、日次学習傾向、mentor-briefingsから、最近の学習傾向、復習、最初に意識する確認ポイントを提示する。

mentor出力は、次のタイミングで行う。

- 学習者が `学習開始` と入力したとき
- 日付が変わった後の最初のプログラミング学習質問
- 確定学習ログ保存後の分析更新時

日付が変わった後の最初の入力では、UserPromptSubmit hookのscriptが当日の `notebook/mentor-briefings/YYYY-MM-DD.md` を準備する。
日付が変わった後の最初の学習質問では、ログ化確認、保存許可、参照範囲確認など、回答待ちで停止すべき状態がある場合だけ、その返答を優先する。
回答待ちでなければ、mentor出力を先に表示し、その後に同じ入力への分類と回答を続ける。

mentorは、次の3つを短く出す。

```md
最近の学習傾向
復習
最初に意識する確認ポイント
```

復習は1件だけ出す。
回答は、Qと折りたたみ可能なAの形にする。

ログが少ない場合、mentorは苦手を断定しない。
根拠が足りない場合は、判断材料が少ないことを伝える。

## 13. 日次処理要件

日次処理は、毎朝の時刻実行ではなく、CodexのUserPromptSubmit hookで入力時に軽く確認する。

基本フローは次の通りである。

```md
ユーザー入力
-> UserPromptSubmit hook
-> .codex/internal/scripts/daily_rollup_on_prompt.rb
-> notebook/mentor-briefings/YYYY-MM-DD.md があるか確認
-> あれば終了
-> なければ前日のLearning Caseを確認
-> notebook/daily-learning-profiles/前日.md を作成
-> notebook/mentor-briefings/今日.md を作成
```

処理済み判定は `.codex/state` ではなく、成果物ファイルの存在で行う。
前日のLearning Caseがない場合でも、当日のmentor-briefingsには「判断材料が少ない」ことを残し、同じ日に何度も日次処理が走らないようにする。
hookの通常実行時は、当日のmentor-briefingsが存在すれば何も出力しない。

## 14. 苦手傾向要件

苦手傾向は、Learning Caseと承認済み学習ログを主な根拠にして判断する。
ログ化されなかったプログラミング学習質問も、Learning Case内の状態更新として補助的に扱う。
日次学習傾向ファイルは、1日のLearning Caseから質問分類件数、苦手種類候補の集計、観察パターン、関連技術語、繰り返し候補、learner-profile / Memory反映候補をまとめる。

苦手種類は次の3つに固定する。

```md
技術知識
構造理解
思考プロセス
```

技術知識と構造理解を優先する。

苦手判定は、技術名ではなく観察パターンの繰り返しを中心に行う。
1回だけ出たものは内部観察として残し、苦手とは断定しない。
同じ観察パターンが2回出た場合、または複数回同じ考え方で間違っている場合は苦手候補にする。
同じ観察パターンが3回以上出た場合、または複数日にまたがって明確に出た場合は苦手傾向候補にする。
learner-profile.mdへ長期傾向として反映する前に、学習者の肯定または修正を確認する。
学習者が否定または修正した場合は、古い見立てを弱めるか表現を修正する。
単発の質問や環境固有の一時的なエラーだけで、苦手と断定しない。

mentor Agent専用MEMORYには、次の項目を保存する。

```md
日付
分類
つまずき
苦手種類
観察パターン
関連技術語
確信度
出現回数
根拠ログ
```

確信度は内部管理として扱う。
学習者には通常、確信度を表示しない。
通常表示と復習候補では、確信度 `中` または `高` を優先する。

## 15. 設定要件

`.codex/config.toml` は、実際にAgentの動作へ適用する設定ファイルである。
`.codex/config.defaults.toml` は、設定検証の基準であり、通常の設定変更では編集しない。

config keyとして残す条件は次の通りである。

- `AGENTS.md`、Skill、hook、scriptのいずれかが、その値に応じて実際に振る舞いを変える。
- 変更しても、保存許可、明示範囲参照、秘密情報保護などの安全原則を壊さない。
- 型、許可値、範囲を `.codex/config.defaults.toml` とRubyチェッカーで検証できる。
- ドキュメントを書き換えずに運用上切り替えたい理由がある。

config keyにしないものは次の通りである。

- 保存許可なしに確定保存しない、明示範囲だけ見る、秘密情報を見ない、などの安全原則。
- 質問分類や苦手種類など、Agentの固定語彙として扱うもの。
- 現在のSkill、hook、scriptが読んでいない将来用の値。

現行の設定は次の3つに絞る。

| key | 役割 |
| --- | --- |
| mentor_start_advice_mode | mentor表示のタイミング |
| agent_trace_mode | Agent経路の表示粒度 |
| scope_listing_max_depth | ディレクトリ一覧確認の最大深度 |

設定に問題がある場合、Agentは影響する処理だけを止め、修正候補を出す。
学習者の承認なしに `.codex/config.toml` を自動修正しない。

## 16. agent_trace要件

`agent_trace_mode` が `brief` または `detailed` の場合、回答時にどの処理経路を通ったかを表示する。

`brief` では、学習者が流れを確認できる短い表示にする。

```md
Agent経路: UserPromptSubmit hook -> daily-rollup-script -> config-guard -> mentor -> classifier -> scope-reader -> learning-log-workflow -> feature-answer -> learning-log-workflow
```

`detailed` は保守確認用であり、通常学習では多用しない。

## 17. 運用要件

保守者が修正する場合、まず変更対象が次のどれかを分ける。

- main Agentの全体ルール
- 回答分類
- 参照範囲
- Learning Case一次記録
- ログ保存
- 日次hook/script
- mentor分析
- 設定検証
- 表示文言

実際の修正先は、`AGENTS.md`、対象Skill、`.codex/config.toml`、mentor Agent定義のいずれかを優先する。
要件定義書だけを直しても、Agentの動作ルールとして確実に効くとは限らない。

Rubyチェッカーは、Agent本体ではなく、設定値と保存済み分類ラベルの最小整合性を確認する補助である。

## 18. 成功条件

ProgrammingAIは、次の状態を満たすことを成功条件とする。

- `main Agent`、回答系Skill、共通制御Skill、mentor Agentの違いを説明できる。
- `feature / unit / assess / error` の分類基準と回答先を説明できる。
- `learning-cases`、`learning-logs`、`notebook/daily-learning-profiles`、`notebook/mentor-briefings`、`.codex/hooks.json`、`.codex/internal/scripts`、`.codex/agents/mentor/MEMORY.md` の役割を混同しない。
- 苦手判定は観察パターンの繰り返しを中心に行い、関連技術語だけで苦手を固定しない。
- `agent_trace` を見て、どの処理経路を通ったか読める。
- 修正前に、見るファイル、変更候補、検証方法を並べられる。
- 学習者に対して、答えだけでなく確認順序と再利用できる考え方を返せる。
- 確定学習ログは、学習者の承認後だけ保存される。
- 日次処理は成果物ファイルの存在で二重実行を避ける。
- mentorは、根拠が少ない苦手を断定しない。

## 19. 変更時の原則

要件を変更する場合は、次の順番で確認する。

1. 課題意識と目的に反していないか。
2. 学習者の自立を助ける変更か。
3. 保存、参照範囲、秘密情報、mentor分析に危険な副作用がないか。
4. 正本である `AGENTS.md` または対象Skillにも反映が必要か。
5. 保守ガイドやSmoke Testの確認手順も更新が必要か。

要件定義書は、Agentを複雑にするためではなく、判断基準を保守しやすくするために使う。
