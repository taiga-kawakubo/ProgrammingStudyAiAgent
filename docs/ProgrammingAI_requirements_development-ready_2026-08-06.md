## 1. 目的

ProgrammingAIは、プログラミング学習者が自立してプログラムを記述できるようになることを支援する、Codex上で動くローカルフォルダ型Agentである。

学習者が分からない内容に対して、答えをそのまま渡すのではなく、考え方、処理の流れ、確認順序を中心に解説する。さらに、学習ログとメンター機能を通じて、学習者の苦手傾向を把握し、復習と改善提案を行う。

## 2. 基本方針

- ProgrammingAIは、Codex秘書の構成を参考にした独立したプログラミング学習支援Agentとする。
- ProgrammingAIは、Codex上で動くローカルフォルダ型Agentとする。
- 回答は基本的に日本語で行う。
- HTML、CSS、その他のプログラミング言語は、説明や成果物に必要な場合のみ使用する。
- 学習者が明示した範囲のみ参照する。
- 最初は考え方と確認順序を優先し、必要な場合だけ修正案やコード例を提示する。
- 各回答の最後に、軽い理解確認を1つ入れる。

## 3. 対象範囲

本書では、機能を簡易版と完成版に分けない。
ProgrammingAIは、しっかり作ったAgentAIとして要件を定義し、まとまった機能単位ごとに実装チェックポイントを設けて動作確認する。

### 3.1 対象

- チャットに直接入力された質問
- 学習者が指定したファイルまたはディレクトリ
- 学習者が貼り付けたコード、エラーメッセージ、説明、設計、テスト内容

### 3.2 対象外

- Notionへの自動保存
- 外部サービスへの自動連携
- 学習者が明示していない範囲の自動探索
- 学習者が指定していないファイル、ディレクトリ、周辺コードの閲覧
- 学習者の承認なしでの確定学習ログ保存
- サブAgentによる直接のファイル更新

### 3.3 実装チェックポイント

要件定義では、機能を完成度で分けるのではなく、実装チェックポイントで分ける。

実装チェックポイントとは、1つのSkill、サブAgent、または一連の学習フローが形になった段階で、ダミー入力を使って実際に動作するか確認する単位である。

各実装チェックポイントには、次の内容を定義する。

- 対象となるSkillまたはサブAgent
- ダミー入力
- 期待する出力
- 作成または更新されるファイル
- 合格条件
- 不合格だった場合に見直す要件箇所

各実装チェックポイントでは、ダミー検証で期待した値が出るまで先に進まない。
期待値と実出力がずれた場合は、次の順番で繰り返し修正する。

```md
1. 期待値との差分を特定する
2. 原因がサブAgent定義、Skill定義、入力条件、期待値のどこにあるかを分ける
3. サブAgent定義またはSkill定義を修正する
4. 同じダミー入力で再検証する
5. すべての合格条件を満たすまで次のチェックポイントへ進まない
```

同じ原因で3回連続して失敗した場合は、次へ進まず、重要判断として学習者へ確認する。
この場合も、合格しないまま次のサブAgentやSkillの実装チェックポイントへ進んではならない。

たとえば、メンターAgentが形になった段階では、ダミーの確定学習ログを複数用意し、最近の学習傾向、復習、苦手分野の判定、根拠ログリンクの表示が想定通り動くかを確認する。

この方式により、完成形を削らずに、作った単位ごとに動作確認しながら要件を育てる。

### 3.4 要件定義の進め方

要件定義は、学習者にすべての細部を逐一確認しながら進めるのではなく、Agentが仮設計を作成し、重要な判断だけ学習者へ確認する形式で進める。

Agentが裁量で仮決定してよい内容は次の通りである。

- 見出し名、説明順序、テンプレート内の細かい表現
- ダミー質問、ダミー学習ログ、実装チェックポイントの入力例
- 各Skillの入力、出力、禁止事項の初期案
- 各ディレクトリやファイルの説明文
- 合格条件の具体例
- エラー文、警告文、確認文の文言案

Agentが必ず学習者へ確認する内容は次の通りである。

- ProgrammingAIの目的や学習体験が変わる判断
- 学習者が見る表示内容に強く影響する判断
- 苦手傾向、学習者像、プロフィールの扱いに関する重要判断
- 参照範囲、秘密情報、外部連携、ファイル削除、保存期間に関する判断
- 学習者の承認なしに進むか止まるかに関する判断
- ディレクトリ構成や責務分離を大きく変える判断
- 実装チェックポイントで動作しなかった場合の方針変更

Agentが裁量で作成した内容は、要件定義書上では確定案として扱う。
ただし、学習者が違和感を示した場合は、その時点で修正する。

この進め方により、要件定義の速度を上げつつ、重要な設計判断は学習者が確認できる状態を保つ。

### 3.5 参照範囲の禁止ルール

ProgrammingAIは、学習者が明示した範囲以外を参照してはならない。

明示された範囲だけでは回答に必要な情報が不足する場合、Agentは不足している参照範囲を説明し、学習者に追加指定を依頼する。

Agentは、必要そうであるという理由だけで、指定外のファイル、ディレクトリ、周辺コードを自動閲覧しない。

参照許可は、指定の具体度に応じて次のように扱う。

- チャットに貼られた内容: その内容を参照してよい
- 具体的なファイル、行番号、関数名、画面名、エラー発生箇所が指定された場合: 指定された内容を直接参照してよい
- ディレクトリやプロジェクト全体が指定された場合: 指定範囲内の浅い一覧を確認し、候補を提案してから詳細参照の許可を取る

例として、学習者が「viewファイルの〇〇を見てください」「resources/views/books/index.blade.phpを見てください」のように具体箇所を指定した場合、Agentはその指定箇所の内容を直接参照してよい。

参照範囲の扱いは、設定で切り替え可能にする。

初期値は、学習者が明示した範囲を優先する `explicit_only` とする。

```toml
scope_access_mode = "explicit_only"
scope_listing_max_depth = 2
```

参照モードは次の通りである。

- explicit_only: 学習者が明示した範囲のみ参照する
- user_defined_depth: 学習者が指定したディレクトリ内を、指定階層まで一覧確認する
- broad_allowed: 学習者が広い閲覧を許可した場合、必要な範囲をAgent判断で参照できる

`broad_allowed` の場合でも、情報漏洩につながる可能性があるファイル、認証情報、秘密鍵、環境変数、個人情報、学習目的と無関係な機密情報は参照してはならない。

参照禁止の判定は、ファイル名パターンと内容の両方で行う。ファイル名が安全そうに見える場合でも、内容にAPIキー、トークン、パスワード、秘密鍵、個人情報などの兆候がある場合、Agentは参照を止める。

秘密情報らしい内容を検出した場合、Agentは内容を表示せず、次のように学習者へ伝える。

```md
指定範囲内に秘密情報の可能性がある内容が含まれているため、このファイルの参照を停止しました。
学習に必要な範囲だけを伏せ字にして貼り付けるか、別の参照範囲を指定してください。
```

参照範囲の指定が曖昧な場合、Agentは候補となる参照範囲を提案してよい。ただし、候補先の中身を先に閲覧してはならない。

候補提案は、学習者の質問内容、貼り付けられた情報、すでに明示された範囲、一般的なプロジェクト構成から行う。

例:

```md
# 追加で確認したい範囲
routes/web.php または app/Http/Controllers 配下が関係している可能性があります。

# なぜ必要か
URLから処理がどこへ渡るかを確認する必要があるためです。

# 指定してほしいもの
確認してよいファイルまたはディレクトリを指定してください。
例: routes/web.php を見てください / app/Http/Controllers を見てください
```

### 4.1 最小動作ハーネス

Projectが複雑になりすぎないよう、ハーネス確認用ファイルは次の3つだけに絞る。

```md
HARNESS_MAP.md
PROJECT_STRUCTURE.md
SMOKE_TEST.md
```

これらは実装基盤ではなく、理解と確認のための軽量ドキュメントである。
Agentの処理や設定を増やす目的ではなく、「どこを見ればよいか」「最低限どこまで動けばよいか」を確認するために使用する。

- `HARNESS_MAP.md`: 入力からログ生成までの全体接続を確認する地図
- `PROJECT_STRUCTURE.md`: 各ディレクトリとファイルの役割を確認する説明書
- `SMOKE_TEST.md`: 質問、分類、回答、理解確認、ログ化確認、ログ生成の最低限動作確認リスト

`HARNESS_MAP.md` は、1ページで全体接続だけを確認できる地図に絞る。
詳細仕様ではなく、学習者の質問が入ってから、どのAgent、共通Skill、専用Skillを通り、最終的にどのファイルが生成または更新されるかを確認するために使用する。

`HARNESS_MAP.md` には、主に次の接続だけを記載する。

```md
学習者の質問
→ メインAgent
→ config-guard
→ scope-reader
→ 分類サブAgent
→ 回答サブAgent
→ 理解確認
→ learning-term-manager
→ learning-log-workflow
→ learning-logs / notion-drafts / notebook
```

`HARNESS_MAP.md` には、回答テンプレートの詳細、設定キー一覧、各Skillの詳細手順、全テストケースは記載しない。
それらはREADME、各Skill、`SMOKE_TEST.md` に分けて記載する。

`PROJECT_STRUCTURE.md` は、各ディレクトリと主要ファイルについて、次の3点だけを記載する。

- 何のためにあるか
- 誰が更新するか
- 学習者が編集してよいか

`PROJECT_STRUCTURE.md` には、実装の詳細や設定値の一覧までは記載しない。
学習者または保守者が「どこを見ればよいか」「どこを修正してよいか」を判断できることを目的とする。

`PROJECT_STRUCTURE.md` の対象は、Agent直下の主要ファイル、`learning-cases/`、`learning-logs/`、`notion-drafts/`、`notebook/`、`.codex/config.toml`、`.codex/config.defaults.toml`、`.codex/skills/` とする。

`SMOKE_TEST.md` の最初の動作確認範囲は、1本の最小フローだけに絞る。
最初の動作確認では、すべての分類やメンター更新まで一度に確認対象に含めず、次の流れが1回通ることを確認する。

```md
質問
→ 分類
→ 回答
→ 理解確認
→ ターム境界判定または明示的な要約依頼
→ 学習ログ候補
→ 保存許可
→ ローカル学習ログ生成
```

この最小フローが通ったあとで、`feature`、`unit`、`assess`、`error`の各分類、メンター更新、設定エラー時の挙動を追加確認する。

ハーネス確認用ファイルは、この3ファイル以外に増やさない。
複雑な自動テスト基盤や追加管理ファイルは、実装チェックポイントで必要性が確認された場合に追加を検討する。

## 5. Agent構成

### 5.1 メインAgent

メインAgentは、学習者との会話、参照範囲の確認、サブAgentへの依頼、学習ターム管理、ログ化フロー、プロフィール更新を管理する。

主な責任は次の通りである。

- 学習者の入力を受け取る
- `.codex/config.toml` を使用する前に、config-guardを必ず呼び出す
- 参照範囲を確認する
- 分類サブAgentへ質問分類を依頼する
- 分類結果に応じて回答サブAgentへ依頼する
- 回答本文を学習者へ提示する
- 理解確認を行う
- 理解確認への返答や新しい学習質問への移行から学習ターム終了候補を判断する
- 明示的な要約依頼では、ログ候補作成と保存許可確認を分ける
- 保存拒否時は、確定学習ログと軽量メモを保存しない
- 確定学習ログ、Notion貼り付け用ドラフト、日次学習傾向ファイルを管理する
- learner-profile.mdへの反映可否を判断する

### 5.2 分類サブAgent

分類サブAgentは、学習者の質問を次のいずれかに分類する。

- feature
- unit
- assess
- error

質問分類はこの4つに固定する。
`summary` は明示的な要約依頼やログ化契機、`test` はテストコードに関する技術領域または副分類として扱い、質問分類にはしない。

分類サブAgentの出力は次の通りである。

- 分類
- 分類理由
- 確信度
- 不足情報

不足情報がある場合、メインAgentは原則として回答前に学習者へ確認する。ただし、軽微な不足情報の場合は、仮定を明示して回答してよい。

分類サブAgentは、回答本文を作成しない。
分類サブAgentは、質問分類、分類理由、確信度、不足情報、回答前確認の要否だけを返す。

分類サブAgentは、次の優先順位で分類する。

```md
1. error: エラーメッセージ、失敗、動かない、例外、テスト失敗が中心の場合
2. assess: 正しいか、問題ないか、十分か、実務で使えるか、評価してほしい場合
3. unit: 関数、メソッド、API、コード一文、式、構文の意味が中心の場合
4. feature: 複数ファイル、機能全体、処理の流れ、データの流れが中心の場合
```

複数に当てはまる場合は、学習者が最初に解決すべき問題を優先して分類する。
たとえば、エラー文が提示されている場合は、コード全体の相談に見えても原則として `error` を優先する。
「この理解で合っているか」という評価依頼が中心の場合は `assess` を優先する。

`fetchが分からない` のように単体理解にも全体理解にも見える質問は、提示情報から判断する。
`fetch()` というAPIや一文の意味を知りたい場合は `unit`、画面からController/APIまでの通信の流れを知りたい場合は `feature` とする。
判断に必要な情報が不足している場合は、不足情報として返す。

### 5.3 featureサブAgent

featureサブAgentは、機能全体、複数ファイルのつながり、処理やデータの流れを説明する。

扱う内容の例は次の通りである。

- 機能全体がどのように動いているか
- 複数のコードがどのようにつながっているか
- 各ファイルがどのような役割を持っているか
- データや処理の流れ

### 5.4 unitサブAgent

unitサブAgentは、一つのメソッド、関数、コード一文の意味を分解して説明する。

扱う内容の例は次の通りである。

- コード一文の処理内容
- メソッドや関数の役割
- 引数、戻り値、実行結果
- 一文を分解して読む手順

### 5.5 assessサブAgent

assessサブAgentは、学習者が作成したコード、説明、設計、テスト、理解内容を評価する。

単に正解、不正解を判定するのではなく、現在の理解段階と次に改善すべき点を明確にする。

### 5.6 errorサブAgent

errorサブAgentは、エラー内容を診断し、確認順序、原因仮説、修正案、検証方法を整理する。

原因をすぐに断定せず、可能性の高い順に仮説を出し、確認する順番を先に示す。

### 5.7 mentorサブAgent

mentorサブAgentは、学習ログや日次学習傾向ファイルをもとに、学習者の傾向、苦手、成長している点を分析する。

現行実装では、mentorだけを独立Agentとして `.codex/agents/mentor/` に配置する。
mentor専用の `MEMORY.md` は、learning-casesとlearning-logsから抽出した苦手分析ログを保存する。

主な責任は次の通りである。

- 承認済み学習ログから学習者の苦手傾向を確認する
- ログ化されなかった質問の軽量メモも補助情報として参照する
- 苦手傾向に該当する内容を復習候補として優先する
- 学習開始時に最近の学習傾向、復習、確認ポイントを提示する
- 日付が変わった後の最初のプログラミング学習質問でも、学習開始時としてmentor分析を行う
- 確定学習ログ保存時に、mentor専用MEMORYを更新する
- 4日に1回、苦手傾向の仮説を提示し、学習者に確認する
- 修正された苦手傾向をlearner-profile.mdへ反映するための更新案を作る

日付が変わった後の最初のプログラミング学習質問では、進行中の学習タームが残っていても、ログ化確認や保存許可など回答待ちで停止すべき状態でなければmentor出力を先に表示する。
古い `current-term` があることだけを理由に、日次mentor出力を省略しない。

### 5.8 サブAgentの作成対象

ProgrammingAIでは、次のサブAgentを作成対象として扱う。

```md
main: 学習者との会話、共通Skill呼び出し、サブAgent依頼、保存判断を行う
classifier: 質問分類、分類理由、確信度、不足情報を返す
feature: 機能全体、複数ファイル、処理とデータの流れを説明する
unit: コード一文、関数、メソッド、API、構文を分解して説明する
assess: 学習者のコード、設計、説明、テスト、理解内容を評価する
error: エラー内容、原因仮説、確認順序、修正案、検証方法を整理する
mentor: 学習ログから傾向、苦手、復習、確認ポイントを提示する
```

各サブAgentは、独立した外部プロセスとして作るのではなく、メインAgentが役割定義とSkillを呼び分ける形式で実現する。
サブAgentは専門的な見立てと回答案を返し、ファイル保存やプロフィール更新の確定処理はメインAgentが行う。

各サブAgentを作成した段階で、対応するSkillとセットで実装チェックポイントを実行する。
期待した値が出ない場合は、サブAgent定義またはSkill定義を修正し、再検証する。

## 6. Skill構成

### 6.1 専用Skill

各サブAgentは、それぞれ専用Skillファイルを持つ。

```md
.codex/skills/classifier/SKILL.md
.codex/skills/feature-answer/SKILL.md
.codex/skills/unit-answer/SKILL.md
.codex/skills/assess-answer/SKILL.md
.codex/skills/error-answer/SKILL.md
.codex/skills/mentor/SKILL.md
```

各専用Skillには、次の項目を必ず記載する。

```md
# 目的
# 入力
# 出力
# 処理手順
# 禁止事項
# メインAgentへ返す管理情報
# ダミー検証
# 合格条件
# 不合格時の修正方針
```

専用Skillは、回答本文や見立てを作成するための手順を定義する。
専用Skillは、原則としてファイルを直接作成、更新、削除しない。
保存、更新、削除が必要な場合は、メインAgentへ更新案として返す。

### 6.2 共通Skill

共通Skillは責務ごとに分ける。

```md
.codex/skills/config-defaults-provider/SKILL.md
.codex/skills/config-defaults-provider/templates/config.toml
.codex/skills/config-defaults-provider/templates/config.defaults.toml
.codex/skills/config-guard/SKILL.md
.codex/skills/scope-reader/SKILL.md
.codex/skills/learning-term-manager/SKILL.md
.codex/skills/learning-log-workflow/SKILL.md
.codex/skills/profile-memory/SKILL.md
```

各共通Skillの役割は次の通りである。

- config-defaults-provider: `.codex/config.toml` の初期内容と、`.codex/config.defaults.toml` の初期チェック定義を、Skill内テンプレートから返す
- config-guard: `.codex/config.toml` の形式チェック、影響範囲の判定、修正案の作成を管理する
- scope-reader: 学習者が明示した参照範囲を確認し、指定外の参照を禁止する
- learning-term-manager: 学習ターム、採番、metadata.tomlを管理する
- learning-log-workflow: ターム境界、明示的な要約依頼、Agent判断の軽量メモ、ログ候補、保存許可、確定保存、Notionドラフト作成を管理する
- profile-memory: 日次学習傾向、learner-profile.md、苦手傾向の反映を管理する

各共通Skillには、次の項目を必ず記載する。

```md
# 目的
# 入力
# 出力
# 処理手順
# 禁止事項
# エラー時の扱い
# ダミー検証
# 合格条件
# 不合格時の修正方針
```

共通Skillは、複数のサブAgentで共有する判断、状態管理、保存フロー、設定確認を扱う。
共通Skillがファイル作成や更新を伴う場合でも、学習者確認が必要な処理はメインAgentが確認してから実行する。

Skill作成後は、対応する実装チェックポイントを必ず実行する。
ダミー検証で期待値が出ない場合、Skill定義を修正し、同じダミー入力で再検証する。
合格するまで、次のSkill作成または統合チェックへ進まない。

### 6.3 Skill作成仕様一覧

各Skillは、次の作成仕様を満たすものとして一括作成する。

| Skill | 主な入力 | 主な出力 | ダミー検証の観点 |
| --- | --- | --- | --- |
| classifier | 質問本文、貼り付け内容、参照範囲、進行中ターム | 分類、分類理由、確信度、不足情報、確認要否 | 8件のダミー質問を期待分類へ分けられる |
| feature-answer | 質問本文、分類結果、許可済み参照範囲、参照済みコード | feature回答、理解度候補、苦手候補、追加参照範囲 | 未確認のRoute/Controller/DB保存を断定しない |
| unit-answer | 質問本文、分類結果、対象コード一文または関数 | unit回答、理解度候補、苦手候補、学習ログ化候補 | 一文を部品に分解して説明できる |
| assess-answer | 評価対象のコード、説明、設計、テスト、理解内容 | 評価、改善案、理解度候補、苦手候補 | 正誤だけでなく改善点を返せる |
| error-answer | エラー文、実行状況、提示コード、参照範囲 | エラー意味、原因仮説、確認順序、修正案、検証方法 | 原因を断定せず確認順序を先に出せる |
| mentor | learning-cases、確定学習ログ、mentor専用MEMORY、日次学習傾向、learner-profile.md | 最近の傾向、復習1件、確認ポイント、苦手候補、mentor MEMORY更新案 | 確信度 `中` 以上の候補だけを通常表示対象にし、確信度の値そのものは通常表示しない |
| config-defaults-provider | なし、または復旧対象キー | config.tomlとconfig.defaults.tomlのテンプレート | 必須キー、型、許可値、範囲を返せる |
| config-guard | config.toml、config.defaults.toml | 設定利用可否、警告、エラー、修正案 | TOML、必須キー、型、許可値、範囲を検査できる |
| scope-reader | 学習者指定範囲、質問本文、設定 | 参照可否、追加確認範囲、参照停止理由 | 指定外閲覧と秘密情報参照を止められる |
| learning-term-manager | 入力意図、分類、参照範囲、current-term | ターム作成可否、metadata、status、awaiting | 作成しないケースを正しく判定できる |
| learning-log-workflow | 回答、理解確認、ログ化判断、修正内容 | ログ候補、確定ログ、Notionドラフト候補 | 承認なしで確定保存しない |
| profile-memory | 確定ログ、軽量メモ、復習結果、設定 | 日次傾向、learner-profile更新案、苦手判定 | 苦手認定基準を満たす場合だけ反映する |

各Skillのダミー検証で期待値が出ない場合は、該当Skillの `処理手順`、`禁止事項`、`出力形式`、`合格条件` のいずれかを修正し、同じダミー入力で再検証する。
合格するまで次のSkillまたは統合チェックへ進まない。

config-defaults-providerは、`.codex/config.toml` の初期内容と、`.codex/config.defaults.toml` の初期チェック定義を返すための共通Skillである。

初期値テンプレートは、次の2ファイルとしてSkill内に最初から配置する。

```md
.codex/skills/config-defaults-provider/templates/config.toml
.codex/skills/config-defaults-provider/templates/config.defaults.toml
```

これらのテンプレートファイルは、Agentの現在の動作を直接決める設定ファイルではない。

テンプレートファイルは、`.codex/config.toml` や `.codex/config.defaults.toml` を初期作成、追記、復旧するときの原本として使用する。

テンプレートファイルは、原則として学習者が通常編集する対象にはしない。

テンプレートファイルを変更する場合は、設定変更ではなくAgent設計変更として扱う。

`.codex/skills/config-defaults-provider/templates/config.defaults.toml` は、`.codex/config.toml` と同じ形の初期値一覧ではなく、必須キー、型、初期値、許可値、許可範囲を持つチェック定義として扱う。

主な用途は次の通りである。

```md
1. 初回セットアップ時に `.codex/config.defaults.toml` の初期チェック定義を与える
2. 初回セットアップ時に `.codex/config.toml` の初期内容を与える
3. `.codex/config.toml` が存在しない場合に作成用テンプレートを与える
4. `.codex/config.toml` に必須キーが不足している場合に、該当キーの初期値を与える
5. `.codex/config.defaults.toml` が存在しない場合に復旧用テンプレートを与える
6. `.codex/config.defaults.toml` が壊れている場合に復旧用テンプレートを与える
7. config-guardが修正案を作るときのデフォルト値の根拠を与える
```

config-defaults-providerの出力は次の通りである。

```md
1. テンプレートバージョン
2. `.codex/config.toml` の初期TOML本文
3. `.codex/config.defaults.toml` の初期チェック定義TOML本文
4. 必須キー一覧
5. 各キーのデフォルト値
6. 各キーの値の型
7. 各キーの許可値または許可範囲
8. 作成、追記、復旧時に学習者へ提示する説明
```

config-defaults-providerは、ファイルを直接作成、更新、削除しない。

config-defaults-providerは、作成、追記、復旧の判断も行わない。

作成、追記、復旧が必要かどうかはconfig-guardが判断し、実際の反映はメインAgentが学習者へ確認した後に行う。

メインAgentは、config-defaults-providerの出力を学習者へ提示し、承認された場合だけ `.codex/config.toml` または `.codex/config.defaults.toml` を作成、追記、復旧する。

config-guardは、メインAgentが他の共通SkillやサブAgentへ依頼する前に必ず呼び出す。

config-guardは、`.codex/config.toml` と `.codex/config.defaults.toml` を読み取り、次の内容をメインAgentへ返す。

```md
1. 設定ファイルを使用できるか
2. 形式エラーの有無
3. エラーがある設定キー
4. 影響を受ける機能
5. 通常回答を継続できるか
6. 学習者へ提示するエラー内容
7. 学習者へ提示する修正案
8. 学習者へ提示する警告内容
9. 学習者へ提示する警告箇所
10. 修正案に使用したデフォルト値の根拠
```

config-guardでは、次の4段階をチェック対象とする。

```md
1. TOMLとして読めるか
2. 必須キーがあるか
3. 値の型が正しいか
4. 許可された値、または許可された範囲内か
```

`.codex/config.defaults.toml` は、config-guardがチェック基準として使用するチェック定義ファイルである。

`.codex/config.defaults.toml` には、必須キー、デフォルト値、値の型、許可された値、許可された範囲を定義する。

`.codex/config.defaults.toml` は、`.codex/config.toml` と同じ形の初期値一覧ではなく、設定を検証するための定義として扱う。

`.codex/config.toml` は実際にAgentの動作へ適用する設定ファイルであり、`.codex/config.defaults.toml` は直接の動作設定としては使用しない。

`.codex/config.defaults.toml` は、原則として学習者が通常の設定変更で編集する対象にはしない。

`.codex/config.defaults.toml` を変更する場合は、Agentの設計変更として扱い、変更理由と影響範囲を確認してから更新する。

config-guardは、最初に `.codex/config.defaults.toml` が存在し、TOMLとして読めるかを確認する。

`.codex/config.defaults.toml` が存在しない、または壊れていて読めない場合は、設定チェックを正常実行できない重大エラーとして扱う。

この場合、config-guardは `.codex/config.toml` の自動補完案を作成しない。

この場合、config-guardはconfig-defaults-providerを呼び出し、`.codex/config.defaults.toml` の復旧用テンプレートを取得する。

取得したテンプレートは、学習者への復旧案提示にのみ使用する。

Agentは、学習者の承認なしに `.codex/config.defaults.toml` を作成または上書きしない。

メインAgentは、設定に依存する処理を停止し、通常の会話や設計相談など、設定に依存しない処理だけを継続する。

メインAgentは、学習者へ `.codex/config.defaults.toml` の修復が必要であることを提示する。

`.codex/config.toml` が存在しない場合、config-guardはconfig-defaults-providerから `.codex/config.toml` の初期内容を取得し、作成案をメインAgentへ返す。

メインAgentは、学習者に作成案を提示し、承認された場合だけ `.codex/config.toml` を作成する。

`.codex/config.toml` が存在している場合、config-guardは不足している必須キーだけを確認する。

必須キーが不足している場合、config-guardはconfig-defaults-providerから該当キーの初期値を取得し、追記案をメインAgentへ返す。

この場合、既存の設定値は上書きしない。

また、Agentが知らない設定キーが追加されている場合は、エラーではなく警告として扱う。

未知の設定キーを見つけた場合、config-guardはキー名と警告箇所をメインAgentへ返す。

必須キーが存在しない場合、config-guardはデフォルト値を使った追記案を作成し、メインAgentへ返す。

メインAgentは、学習者に追記案を提示し、承認された場合だけ `.codex/config.toml` に追記する。

メインAgentは、config-guardの結果をもとに、問題がある設定値を使う処理だけを停止する。

scope-readerは、次の4つを明示された参照範囲として扱う。

- チャットに貼られたコードやエラー文
- 学習者が指定したファイルパス
- 学習者が指定したディレクトリパス
- 学習者が指定した行番号、関数名、画面名、エラー発生箇所

scope-readerは、指定されていないファイル、ディレクトリ、周辺コードを参照対象に含めない。追加情報が必要な場合は、メインAgentへ「追加で確認が必要な範囲」を返し、メインAgentが学習者に確認する。

## 7. 権限と責任分離

ここでいう権限は、OS上の厳密な権限ではなく、どのAgentが判断し、どのAgentがファイル更新してよいかの責任分離である。

### 7.1 サブAgentの責任

サブAgentは、専門的な見立てを返す。

- 回答本文を作成する
- 管理情報の更新案を返す
- 原則としてファイルを直接更新しない

管理情報の更新案は、次の4つとする。

- 理解度候補
- 苦手の具体内容候補
- 苦手傾向タグ候補
- 学習ログ化候補

### 7.2 メインAgentの責任

メインAgentは、サブAgentの出力を受け取り、保存ルールに従って反映する。

- 学習者への確認が必要なものは確認する
- 承認済みのものだけを確定学習ログとして保存する
- Agent判断で保存してよい軽量メモだけを日次学習傾向ファイルへ保存する
- 苦手傾向の仮説は、4日に1回の確認後にlearner-profile.mdへ反映する

## 8. 質問分類

### 8.1 feature

featureは、機能全体や複数ファイルのつながり、処理やデータの流れが分からない場合の分類である。

### 8.2 unit

unitは、一つのメソッド、関数、コード一文の意味が分からない場合の分類である。

### 8.3 assess

assessは、学習者が作成したコード、説明、設計、テスト、理解内容を評価する場合の分類である。

### 8.4 error

errorは、エラーメッセージ、実行時の不具合、失敗原因の切り分けを行う場合の分類である。

### 8.5 classifier Skill

classifier Skillは、分類サブAgentが質問分類を行うための専用Skillである。

入力は次の通りである。

- 学習者の質問本文
- 学習者が貼り付けたコード、エラーメッセージ、説明、設計、テスト内容
- 学習者が明示した参照範囲
- 進行中の学習タームがある場合は、その分類と状態

出力は次の形式とする。

```md
classification: feature / unit / assess / error
reason: 分類理由を1〜2文で書く
confidence: high / medium / low
missing_info:
  - 不足情報がある場合だけ書く
need_user_confirmation: true / false
assumption:
  - 軽微な不足情報を仮定して進む場合だけ書く
```

`confidence` は管理情報として使用する。
学習者向けの回答冒頭には、通常は分類と分類理由だけを短く表示する。

`need_user_confirmation` は、回答前に学習者確認が必要かどうかを表す。
分類そのものが不安定な場合、または参照範囲が不足して回答品質に大きく影響する場合は `true` とする。
軽微な不足情報で、仮定を明示すれば回答できる場合は `false` とする。

classifier Skillは、分類結果を返すだけで、回答本文や学習ログ本文は作成しない。

### 8.6 classifier Skillのダミー検証

classifier Skillは、次のダミー質問で分類が安定するか確認する。

```md
1. 「ログイン機能でRoute、Controller、Bladeがどうつながっているか分かりません」
期待分類: feature
理由: 複数ファイルと処理の流れが中心であるため。

2. 「$user->books()->create($data) の意味が分かりません」
期待分類: unit
理由: コード一文とメソッド呼び出しの意味が中心であるため。

3. 「このバリデーションの書き方で問題ありませんか」
期待分類: assess
理由: 学習者が作成したコードの評価依頼であるため。

4. 「Call to undefined method App\Models\User::books() が出ます」
期待分類: error
理由: エラーメッセージの意味と原因切り分けが中心であるため。

5. 「fetchが分かりません」
期待分類: unit
理由: 単語だけならAPIまたは関数の意味を知りたい可能性が高いため。
不足情報: fetch一文の意味なのか、画面からAPIまでの流れなのか。
need_user_confirmation: false
assumption: fetch APIの基本理解として回答し、必要ならfeatureとして掘り下げる。

6. 「fetchでControllerに送った後、DB保存までの流れが分かりません」
期待分類: feature
理由: 画面、通信、Controller、DB保存までの流れが中心であるため。

7. 「このコードでエラーが出ます。私の理解も合っているか見てください」
期待分類: error
理由: エラー解決が最初に解くべき問題であり、assessよりerrorを優先するため。

8. 「このテスト内容で十分ですか」
期待分類: assess
理由: テスト内容の評価依頼であるため。
```

合格条件は、上記8件の分類、分類理由、不足情報、確認要否が期待通りに出ることである。
特に、`error` と `assess` が混ざる質問では、最初に解決すべき問題を優先して分類できることを確認する。

## 9. 回答テンプレート

### 9.1 共通テンプレート

featureとunitは、基本的に次の共通テンプレートを使用する。

```md
# 分類
# 今回の学習テーマ
# つまずきの中核
# 全体像
# 理解ステップ
# 具体例（他でも使える考え方）
# 次に同じ問題が出たら見る順番
# 理解確認
```

featureでは、理解ステップの中で、ファイルの役割、コード同士のつながり、処理とデータの流れを扱う。

unitでは、理解ステップの中で、一文の分解、関数やメソッドの役割、引数、戻り値、実行結果を扱う。

### 9.2 feature-answer Skill

feature-answer Skillは、featureサブAgentが機能全体、複数ファイルのつながり、処理やデータの流れを解説するための専用Skillである。

入力は次の通りである。

- 学習者の質問本文
- classifier Skillの分類結果と分類理由
- scope-readerが許可した参照範囲
- 学習者が貼り付けたコード、ファイル一覧、エラーメッセージ、説明
- 参照済みファイルの内容または抜粋
- 進行中の学習タームがある場合は、そのmetadata.tomlの分類と状態

出力は、9.1の共通テンプレートを使用する。
feature回答では、特に `理解ステップ` を中核とし、次の順番で説明する。

```md
1. 関係するファイルまたはコードの役割
2. ユーザー操作または入力の起点
3. 処理が次に渡る場所
4. データが作られる場所、渡される場所、使われる場所
5. 画面表示、DB保存、API応答などの終点
6. 今回のつまずきが起きやすい接続点
```

feature-answer Skillは、最初から修正案やコード例を出すのではなく、考え方と確認順序を優先する。
コード例を出すのは、学習者が理解するために必要な場合、または確認順序だけでは説明が不十分な場合に限る。

feature-answer Skillは、参照していないファイルや処理を断定してはならない。
たとえば、BladeやJavaScriptの `fetch` が提示されているだけで、実際のRoute、Controller、APIエンドポイント、DB保存処理が存在すると断定してはならない。
参照範囲が不足している場合は、追加で確認したい範囲と、その理由を提示する。

feature-answer Skillが返す管理情報の更新案は次の通りである。

- 理解度候補
- 苦手の具体内容候補
- 苦手傾向タグ候補
- 学習ログ化候補
- 追加で確認したい参照範囲

feature-answer Skillは、ファイル作成、ファイル更新、学習ログ保存、プロフィール更新を直接行わない。

### 9.3 feature-answer Skillのダミー検証

feature-answer Skillは、次のダミー質問で回答の安定性を確認する。

```md
1. 「ログイン機能でRoute、Controller、Bladeがどうつながっているか分かりません」
入力条件: routes/web.php、LoginController、login.blade.php が明示されている
期待出力: Route -> Controller -> Blade の役割と処理の流れを説明する
合格条件: 各ファイルの役割、処理の起点、データの流れ、次に見る順番が出る

2. 「fetchでControllerに送った後、DB保存までの流れが分かりません」
入力条件: Blade内のfetchコードだけが提示されている
期待出力: fetch側から分かることと、まだ確認できないRoute/Controller/DB保存を分ける
合格条件: 未参照のRoute、Controller、DB保存処理を断定せず、追加で確認したい範囲を提示する

3. 「この一覧画面で、ControllerからBladeへ渡した値がどこで表示されているか分かりません」
入力条件: Controllerのreturn viewとBladeのforeachが提示されている
期待出力: Controllerで作った変数、viewへの受け渡し、Bladeでの表示箇所を順に説明する
合格条件: 変数名、渡る方向、表示される場所を分けて説明する

4. 「この機能の全体像が分かりません」
入力条件: 機能名や参照範囲が不明
期待出力: 回答前に、確認したい機能名または参照範囲を質問する
合格条件: 参照範囲を勝手に探索せず、候補だけを提示する

5. 「フォーム送信からバリデーション、保存、一覧表示までの流れを知りたいです」
入力条件: routes、Controller、Request、Model、Bladeが明示されている
期待出力: 入力 -> validation -> 保存 -> redirectまたは表示 -> 一覧反映の順に説明する
合格条件: 処理の流れとデータの流れを混同せずに説明する
```

合格条件は、上記5件で、参照済み情報と未確認情報を分け、学習者が次に同じ問題で見る順番を自力で使える形で提示できることである。

### 9.4 assess専用テンプレート

```md
# 分類
# 現状の確認
# 評価
# つまずき（assess）の中核

# 具体例（他でも使える考え方）
```

## 10. 学習ターム管理

学習タームとは、1つの質問とその追質問、回答、理解確認、ログ保存判断までを含む学習の一区切りである。

learning-term-managerは、入力意図ゲート、分類サブAgentの分類結果、scope-readerの参照範囲確認をもとに、回答生成の前に学習タームを作成する。

質問を受け取った直後には、原則として学習タームを作成しない。雑談、未確定の相談、参照範囲が不足している質問までディレクトリ化して散らかることを防ぐためである。

学習ターム作成時には、question.md、context.md、metadata.tomlを初期作成する。answer-draft.mdは回答生成後、log-draft.mdはログ化候補作成時に更新する。

learning-term-managerは、学習ターム作成前に「学習ターム作成ゲート」を実行する。

学習ターム作成ゲートは、2段階で実行する。

第1段階は、入力意図ゲートである。メインAgentは、学習者のchat内容を読み、入力意図を次のいずれかに仮分類する。

```md
learning_question: プログラミング学習内容の質問
follow_up: 進行中の学習タームへの追質問
mentor_command: 学習開始、復習、最近の傾向確認などのメンター操作
log_workflow: ログ化、ログ修正、修正完了などの学習ログ操作
profile_update: learner-profile.mdや苦手傾向の修正
config_change: 設定変更
design_discussion: ProgrammingAI自体の要件定義や設計相談
chat_only: 雑談
unclear: 判断に必要な情報が不足している
```

第2段階は、作成判定である。入力意図、進行中の学習ターム、分類結果、参照範囲確認の状態をもとに、次のいずれかの判定を返す。

```md
create_new: 新しい学習タームを作成する
attach_to_active: 進行中の学習タームへの追質問として扱う
no_term: 学習タームを作成しない
ask_clarification: 学習ターム化の前に確認する
```

判定結果には、必ず理由を含める。

```md
判定: no_term
理由: 設定変更のみの依頼であり、プログラミング学習内容の質問ではないため。
```

判定結果は、metadata.tomlへ保存する前に、メインAgentが保持する進行状態として扱う。no_termやask_clarificationの場合は、新しいディレクトリを作成しない。

進行中の学習タームを判断するための状態は、`.codex/state/current-term.toml` に保存する。

current-term.tomlは、学習ログではなく、Agentの進行管理用の一時的な状態ファイルである。会話全文やコード全文は保存しない。

```toml
active = true
term_id = "2026-08-05-001-route-flow"
term_path = "learning-cases/2026-08-05/001-route-flow"
classification = "feature"
status = "answer_created"
awaiting = "understanding_check"

referenced_scope = ["routes/web.php", "app/Http/Controllers"]
last_user_intent = "follow_up"
updated_at = "2026-08-05T14:30:00+09:00"
```

metadata.tomlは各学習タームの管理台帳、current-term.tomlは現在アクティブな学習タームを示すポインタとして扱う。

利用者向けには、次のように説明する。

```md
metadata.toml:
各学習タームごとの管理台帳です。
その学習タームの分類、参照範囲、回答状態、ログ化状態などを記録します。

current-term.toml:
現在アクティブな学習タームを示すポインタです。
Agentが「今どの学習タームの途中か」「次に何を待っているか」を判断するために使います。
```

current-term.tomlの`active`は、学習ログの保存、破棄、または必要な軽量メモ保存の判断が終わった時点で`false`にする。

ログ化する場合は、確定学習ログとNotion貼り付け用ドラフトの生成が完了した後に`active = false`とする。

ログ化しない場合は、必要な軽量メモを日次学習傾向ファイルへ反映した後に`active = false`とする。

理解確認が終わっただけでは、原則として`active = false`にしない。ログ化判断や軽量メモ保存が残っている可能性があるためである。

学習者が途中で別タームに移る場合、現在の学習タームは`paused`として保留できる。

保留中の学習タームは、`.codex/state/paused-terms.toml` に保存する。

```toml
[[paused_terms]]
term_id = "2026-08-05-001-route-flow"
term_path = "learning-cases/2026-08-05/001-route-flow"
classification = "feature"
status = "paused"
paused_reason = "学習者が別テーマのエラー確認に移ったため"
paused_at = "2026-08-05T15:00:00+09:00"
resume_hint = "RouteからControllerへの処理の流れの理解確認から再開"
```

途中で別テーマに移った可能性がある場合、メインAgentは学習者へ確認する。

```md
今の学習タームを保留して、新しいタームを開始しますか？
```

学習者が承認した場合、現在のタームのstatusを`paused`にし、paused-terms.tomlへ記録する。その後、current-term.tomlを新しい学習タームへ切り替える。

学習者が「さっきのRouteの話に戻る」のように伝えた場合、メインAgentはpaused-terms.tomlから候補を提示し、学習者が選んだタームをcurrent-term.tomlへ戻す。

pausedはclosedではない。ログ化判断、理解確認、追質問への回答などが残っている可能性があるため、再開可能な状態として扱う。

実装上は、メインAgentが次の順番で判断する。

```md
1. chat内容から入力意図を判定する
2. 進行中の学習タームがあるか確認する
3. 入力意図がfollow_upの場合は、既存タームへ紐づける
4. 入力意図がlearning_questionの場合は、classifierとscope-readerへ進む
5. 分類と参照範囲が揃ったら、新しい学習タームを作成する
6. 入力意図が管理操作や雑談の場合は、学習タームを作成しない
7. 判断できない場合は、学習者へ確認する
```

途中で別テーマへ移る場合は、次の順番で処理する。

```md
1. chat内容から別テーマへ移った可能性を検知する
2. 学習者に、現在のタームを保留して新しいタームを開始するか確認する
3. 承認された場合、現在のタームをpausedにする
4. paused-terms.tomlへ保留タームを記録する
5. current-term.tomlを新しいタームへ切り替える
```

学習タームを作成しないケースは次の通りである。

- 雑談
- 設定変更だけの依頼
- 「学習開始」などメンター起動だけの入力
- 参照範囲が不足していて、まだ回答に入れない質問
- ログ化、ログ修正、プロフィール修正など、既存タームや記憶の管理操作
- 既存の学習タームに対する追質問
- 要件定義、設計相談、Agent自体の仕様相談など、ProgrammingAIの運用設計に関する会話

既存の学習タームに対する追質問の場合、新しいディレクトリは作成せず、進行中の学習タームに紐づける。

参照範囲が不足している場合は、学習タームを作成せず、scope-readerの追加指定フローへ戻す。

学習ターム作成ゲートは、次の観点で判断する。

- 入力がプログラミング学習内容の質問か
- feature / unit / assess / error のいずれかに分類できるか
- 回答に必要な参照範囲が確認済みか
- 進行中の学習タームへの追質問か
- 設定、ログ、プロフィール、メンター起動などの管理操作か
- 学習者が新しい学習テーマとして扱う意思を示しているか

学習タームの終了候補は、Agentが判断し、最後に学習者へ確認する。

終了候補の例は次の通りである。

- 質問内容が変わった場合
- 理解確認が完了した場合
- 修正と検証が完了した場合
- 学習者が別テーマへ移った場合

回答がない場合に次へ進むかどうかは、設定で切り替え可能にする。

```toml
confirmation_mode = "strict_stop"
```

- strict_stop: 必ず停止する
- agent_decides: Agentが判断して先に進む

## 11. ディレクトリとファイル管理

### 11.1 日付ディレクトリ方式

learning-cases、learning-logs、notion-draftsは、すべて日付ディレクトリ方式とする。

```md
learning-cases/YYYY-MM-DD/001-topic/
learning-logs/YYYY-MM-DD/001-topic.md
notion-drafts/YYYY-MM-DD/001-topic.md
```

### 11.2 学習タームの採番

各学習タームは、日付ごとに001、002、003の3桁連番で自動採番する。

topic部分は、Agentが学習内容から短い英語スラッグを自動生成する。

例:

```md
learning-cases/2026-08-05/001-route-flow/
learning-cases/2026-08-05/002-validation-error/
```

### 11.3 学習ターム内の必須ファイル

各学習タームには、次の5ファイルを作成する。

```md
question.md
context.md
answer-draft.md
log-draft.md
metadata.toml
```

役割は次の通りである。

- question.md: 学習者の質問
- context.md: 参照した範囲
- answer-draft.md: 回答下書き
- log-draft.md: 学習ログ下書き
- metadata.toml: 学習タームの分類、状態、参照範囲などの管理情報

## 12. metadata.toml

metadata.tomlは、学習内容そのものではなく、学習タームをAgentが管理するための情報ファイルである。

例:

```toml
term_id = "2026-08-05-001-route-flow"
date = "2026-08-05"
sequence = 1
topic_slug = "route-flow"

classification = "feature"
classification_reason = "複数ファイルのつながりと処理の流れを質問しているため"
confidence = "high"

status = "answer_created"
awaiting = "understanding_answer"
log_status = "none"
log_trigger = "none"
save_permission = "not_requested"
light_memo_status = "none"
notion_draft_created = false

referenced_scope = ["routes/web.php", "app/Http/Controllers"]
created_at = "2026-08-05T10:00:00+09:00"
updated_at = "2026-08-05T10:30:00+09:00"
```

### 12.1 status一覧

metadata.tomlとcurrent-term.tomlで使用するstatusは、次の通りとする。

```md
created: 学習タームを作成した
answer_created: 回答下書きを作成した
understanding_check: 理解確認への回答を待っている
log_decision: ログ化する/しないの判断を待っている
log_draft_created: 学習ログ候補を作成した
log_confirming: 学習者の修正または保存判断を待っている
log_saved: 確定学習ログを保存した
notion_draft_created: Notion貼り付け用ドラフトを生成した
log_discarded: ログ候補を破棄した
light_memo_saved: 軽量メモを保存した
paused: 途中で別テーマへ移ったため保留中
closed: 学習タームを終了した
```

statusは、Agentが次に何を行うべきかを判断するための進行信号である。学習者に必ず表示するものではない。

### 12.2 awaiting一覧

awaitingは、Agentが次に何を待っているかを表す。

```md
none: 何も待っていない
scope_confirmation: 参照範囲の確認を待っている
user_clarification: 質問内容や前提の確認を待っている
understanding_answer: 理解確認への回答を待っている
log_decision: ログ化する/しないの判断を待っている
log_revision: 学習ログ候補の修正または確認完了を待っている
save_permission: ログ候補を保存するかどうかの返答を待っている
resume_choice: 保留中タームの再開選択を待っている
```

awaitingは、学習者が「はい」「修正完了」「2番で」のように短く返答した場合でも、メインAgentが文脈を誤らず判断するために使用する。

### 12.3 想定外返答時の扱い

awaiting中に想定とは違う返答が来た場合、メインAgentは次工程へ進まず、入力意図ゲートへ戻して再判定する。

想定外返答時の基本方針は次の通りである。

- 確定保存しない
- current-term.tomlを不用意にclosedへ変更しない
- ログ化、プロフィール更新、Notionドラフト生成などの確定処理を行わない
- 返答が新しい学習質問の場合は、現在のタームを保留するか確認する
- 返答が管理操作の場合は、現在のawaitingを維持したまま管理操作を処理する
- 判断できない場合は、学習者へ確認する

次の遷移ルールを使用する。

```md
awaiting = scope_confirmation
- 想定: 参照を許可する / 別範囲を指定する / 参照しない
- 想定外: user_clarificationへ移り、確認する
- 新しい学習質問: 現在のタームを保留するか確認する

awaiting = user_clarification
- 想定: 前提や質問内容の補足
- 想定外: 再度、必要な確認点を1つに絞って聞く
- 新しい学習質問: 現在の確認を中断して新規タームにするか確認する

awaiting = understanding_answer
- 想定: 理解確認への回答
- 想定外: 入力意図ゲートへ戻す
- 追質問: 既存タームへの追質問として扱う
- 新しい学習質問: 現在のタームをpausedにするか確認する

awaiting = log_decision
- 想定: ログ化する / ログ化しない
- 想定外: ログ化判断を再確認する
- 新しい学習質問: 現在のタームをpausedにするか確認する

awaiting = log_revision
- 想定: 修正内容 / 修正完了
- 想定外: 修正継続か確定かを確認する
- 新しい学習質問: 現在のタームをpausedにするか確認する

awaiting = save_permission
- 想定: 保存する / 保存しない
- 保存する: 確定学習ログとNotion貼り付け用ドラフトを生成する
- 保存しない: ログ候補を破棄し、軽量メモも保存しない
- 新しい学習質問: 保存判断を先に確認する

awaiting = resume_choice
- 想定: 再開するタームの選択
- 想定外: 候補を再提示し、選択を依頼する
- 新しい学習質問: 保留タームはそのままにして、新しいタームを開始するか確認する
```

想定外返答の確認文は、できるだけ短くする。

```md
今の返答は、ログ化判断ではなく新しい質問として扱いますか？
現在のタームを保留して進めてもよいですか？
```

## 13. 学習ログ

### 13.1 学習ログ化フロー

学習ログは、ターム境界候補、明示的な要約依頼、Agent判断による軽量メモの3つの契機で扱う。
ターム境界候補ではログ化するかを確認し、明示的な要約依頼ではログ候補の作成と保存許可を分ける。

```md
1. Agentが学習ターム終了候補を判断する、または学習者が内容の要約を依頼する
2. ターム境界候補では、学習者に「ログ化する / ログ化しない」を提案する
3. ログ化しない場合は、必要に応じて日次学習傾向ファイルへ軽量メモを残す
4. 明示的な要約依頼またはログ化する返答では、学習ログ候補を提示する
5. 学習者が内容を確認・修正する
6. 学習者が「修正完了」と伝えたら、保存するかを確認する
7. 学習者が保存を許可した場合だけ、承認済み学習ログとしてローカルに保存する
8. 保存した場合だけ、Notion貼り付け用ドラフトを生成する
9. Agentが軽量メモを残す価値があると判断した場合は、確定学習ログを作らず軽量メモだけを保存する
10. 学習者が保存しないと答えた場合は、確定学習ログと軽量メモを保存しない
```

### 13.2 修正方法

学習ログ候補の修正は、基本的にチャット上で行う。

ただし、必要に応じてAgentが生成した下書きファイルを学習者が直接編集できる。誤字、表現、見出し、補足などの微修正は直接編集してよい。

学習者が「修正完了」と伝えた後、Agentは保存許可を確認する。保存許可を受けた時点で確定版として保存する。

学習ログ候補の確認段階では、Agentの見立てが入る項目に **【Agent見立て】** と付ける。

これにより、学習者は「そこは違う」「この表現の方が近い」と修正しやすくなる。

確定版として保存するときは、学習者の修正内容を優先し、必要に応じて **【Agent見立て】** の表記を外す。

README.mdには、学習ログは保存前にチャットまたは下書きファイル上で修正できることを明記する。

### 13.3 確定学習ログの型

確定版の学習ログは、次の型を使用する。

```md
# 学習テーマ
# 質問分類
# 質問した内容
# つまずきの中核
# 学習前の理解
# 学んだ内容
# 処理またはコードの流れ
# 確認したこと
# 次に同じ問題が出たら見る順番
# 他でも使える考え方
# 苦手の具体内容
# 苦手傾向タグ
# 理解度
# 未解決事項
# 次に学習すること
```

learning-log-workflowは、学習ログ候補を作成するときに、各見出しへ何を書くかを判断する記入ルールを持つ。

記入ルールは、`.codex/skills/learning-log-workflow/SKILL.md` にSkillとして定義する。

### 13.4 学習ログ項目の記入ルール

各見出しには、次の内容を書く。

```md
# 学習テーマ
今回の学習内容を一言で表す。質問文そのものではなく、復習時に探しやすいテーマ名にする。

# 質問分類
feature / unit / assess / error のいずれかを書く。必要な場合は副分類も書く。
summaryやtestは質問分類として書かない。summaryはログ化契機、testは技術領域や副分類として扱う。

# 質問した内容
学習者が何を分からなかったのかを簡潔に書く。会話全文は残さない。

# つまずきの中核
表面的な質問ではなく、理解できていなかった中心部分を書く。

# 学習前の理解
質問時点で、学習者がどう理解していたかを書く。分からない場合は「不明」と書く。

# 学んだ内容
解説によって新しく理解した内容を書く。

# 処理またはコードの流れ
必要な場合のみ、処理、データ、ファイル、関数のつながりを書く。不要な場合は「該当なし」と書く。

# 確認したこと
理解や修正が正しいと判断するために確認した内容を書く。

# 次に同じ問題が出たら見る順番
次回、学習者が自力で確認するための順番を書く。

# 他でも使える考え方
今回の内容を、別の機能やプロジェクトでどう応用できるかを書く。

# 苦手の具体内容
今回の学習ログ本文から、具体的に何ができなかったかを抽出して書く。

# 苦手傾向タグ
苦手の具体内容を、種類、分類、技術領域、思考、癖に分けて整理する。

# 理解度
理解できた / 一部あいまい / 要復習 のいずれかをAgentが仮判定し、学習者が修正できる形で書く。

# 未解決事項
今回の学習で解決していない内容を書く。ない場合は「なし」と書く。

# 次に学習すること
今回の内容から続けて学習するとよい項目を一つだけ書く。
```

記入時の制約は次の通りである。

- 会話全文をそのまま保存しない
- コード全文を不要に保存しない
- 学習者が新しく理解したことを中心に書く
- 復習やメンター分析に使える粒度で書く
- Agentの推測は断定せず、候補として書く
- 不明な内容を無理に埋めない
- 学習者の修正を確定版に優先して反映する

### 13.5 理解度

理解度は、Agentが仮判定し、学習者が修正できる形とする。

理解度は次の3段階を使用する。

- 理解できた
- 一部あいまい
- 要復習

### 13.6 苦手の具体内容と苦手傾向タグ

苦手は、まず学習ログ本文から具体的な内容として抽出する。その上で、種類、分類、技術領域、思考、癖に分けてタグ化する。

苦手の種類は、次の3つに固定する。

```md
技術知識:
言語、フレームワーク、ライブラリ、構文、APIなどの知識不足。

構造理解:
ファイルの役割、コード同士のつながり、処理やデータの流れを追う力。

思考プロセス:
原因仮説、設計判断、抽象化、比較、優先順位づけなどの考え方。
```

苦手の種類は、この3分類の中から主分類を1つ選ぶ。必要な場合だけ補助分類を1つ追加してよい。

確認方法や学習の進め方に関する苦手は、独立した種類にはせず、`思考プロセス` または `癖` のタグとして補足する。

技術領域は、広すぎず細かすぎない単位で保存する。

技術領域は、次のような粒度を基準にする。

```md
Laravel
Route
Controller
Blade
JavaScript
Fetch
Validation
Database
Test
```

技術領域は、必要に応じて複数指定してよい。

技術領域は固定リストではなく、初期候補を基本にしつつ、Agentが必要に応じて追加できる。

Agentが新しい技術領域を追加する場合、学習者への事前確認は不要とする。

技術領域は苦手傾向そのものではなく分類補助であるため、追加のたびに学習を止めない。

ただし、追加された技術領域は4日に1回の「最近の学習傾向」で表示し、学習者が違和感を持った場合は修正できるようにする。

Agentが追加した技術領域は、`.codex/config.toml` の `technical_area_custom_candidates` に保存する。

初期候補と追加候補を分ける理由は、Agentが後から追加した分類だけを確認、修正、削除しやすくするためである。

学習者は、Agentが追加した技術領域を後から削除、名前変更、既存候補へ統合できる。

技術領域の削除、名前変更、統合は、`.codex/config.toml` の `technical_area_custom_candidates` に反映する。

技術領域を名前変更または統合しても、過去の確定学習ログ内のタグは書き換えない。

確定学習ログは、その時点の学習記録として保持する。

以後の分析では、`.codex/config.toml` の `technical_area_aliases` を使って、新しい名前へ読み替える。

`technical_area_aliases` は、学習者が直接編集できる。

チャットで修正依頼してもよいし、`.codex/config.toml` を直接編集して読み替え設定を追加、修正、削除してもよい。

学習者が直接編集した場合、Agentは次回使用前に `.codex/config.toml` の共通形式チェックと、`technical_area_aliases` の個別形式チェックを行う。

チェック内容は次の通りである。

```md
1. TOMLとして読み込める
2. technical_area_aliases が配列として定義されている
3. 各要素に from と to がある
4. from と to が空文字ではない
5. 同じ from の重複がない
```

形式に問題がある場合、Agentは `technical_area_aliases` を使う分析だけを停止する。

通常の質問回答、分類、解説は継続する。

形式エラーを確認した場合、Agentは第19章の `.codex/config.toml` 共通修正フローに従い、修正箇所と修正案を提示する。

Agentは、学習者の承認なしに `.codex/config.toml` を自動修正しない。

例:

```md
過去ログのタグ: API通信
読み替え後: Fetch
```

ただし、新しい技術領域を追加する場合は、既存候補で表現できないかを先に確認する。

表記ゆれを防ぐため、同じ意味の技術領域はできるだけ既存の名前に寄せる。

例:

```md
API通信 → Fetch または API
DB → Database
テスト → Test
```

```md
# 苦手の具体内容
- RouteからControllerへ処理が渡る流れを、自分で順番に追えなかった

# 苦手傾向タグ
- 種類: 構造理解
- 分類: feature
- 技術領域: Route / Controller
- 思考: 処理の流れを追う
- 癖: 個別コードから見始める
```

## 17. learner-profile.md

learner-profile.mdは、学習者の固定または半固定情報を管理するファイルである。

```md
notebook/
├── learner-profile.md
├── learning-profile.md
└── daily-learning-profiles/
```

learner-profile.mdには、次の情報を反映する。

- Agent認定の苦手傾向
- 修正済みの苦手傾向
- 得意な進め方
- 学習スタイル
- メンター時の注意点
- 成長している傾向

苦手傾向だけではなく、得意な進め方や学習スタイルも保存する理由は、mentorサブAgentが「何を復習させるか」だけでなく、「どのように説明すると学習者が理解しやすいか」を判断できるようにするためである。

現行実装では、苦手分析の一次的な集計先として `.codex/agents/mentor/MEMORY.md` を使用する。
`learner-profile.md` は、学習者に関する固定または半固定の見立てを保存する場所として扱い、mentor専用MEMORYは、learning-casesとlearning-logsから抽出した苦手候補、確信度、出現回数、根拠ログを保存する場所として分ける。

### 17.1 learner-profile.mdの更新ルール

learner-profile.mdへの反映は、内容の重要度と苦手認定基準によって扱いを分ける。

軽い内容は、Agent判断で仮反映してよい。

苦手傾向は、学習者が自分で判断しづらい内容であるため、基準を満たした場合はAgentが言い切る形で認定してよい。

ただし、学習者が後から修正できるように、根拠ログと認定理由を必ず一緒に残す。

Agent認定の苦手傾向には、管理情報として `確信度` を残す。

確信度は、次の3段階で管理する。

```md
高:
同じ苦手が3回以上出ている、または複数の根拠ログで同じつまずきが明確に確認できる。

中:
同じ苦手が2回出ている、または近い苦手としてまとめられる根拠がある。

低:
苦手の可能性はあるが、根拠ログが少ない、または単発のつまずきに近い。
```

確信度 `低` の苦手傾向は、復習優先順位に入れない。

確信度 `低` の苦手傾向は、学習開始時のメンター表示にも出さない。

確信度 `低` は、learner-profile.mdに観察として保存し、今後同じ内容が繰り返された場合に `中` 以上へ上げる候補として扱う。

確信度 `低` の苦手傾向は、同じ苦手の種類、または近い苦手傾向タグがもう1回出た場合に、確信度 `中` へ上げる。

確信度 `中` の苦手傾向は、同じ苦手が3回以上出た場合、または複数の根拠ログで同じつまずきが明確に確認できる場合に、確信度 `高` へ上げる。

ただし、確信度は学習者向けの通常表示には出さない。

学習者が根拠や判断の強さを確認したい場合だけ、`確信度` を表示する。

```md
## Agent判断で仮反映してよい内容
- 得意な進め方の候補
- 学習スタイルの軽い観察
- 成長している傾向
- 説明方法の好み

## Agentが認定してよい内容
- 基準を満たした苦手傾向の追加
- 近い苦手としてまとめた候補の登録
- 復習優先度への反映

## 学習者の修正を優先する内容
- 学習者が「違う」と伝えた苦手傾向の修正
- 学習者が「違う」と伝えた苦手傾向の削除
- メンター時の注意点
- 学習者像を強く決める内容
```

仮反映した内容は、`状態: 仮反映` として記録する。

仮反映した内容とAgent認定の苦手傾向は、4日に1回の「最近の学習傾向」表示時にまとめて表示する。
ただし、確信度 `低` の苦手候補は、4日に1回の「最近の学習傾向」でも通常は表示しない。
確信度 `低` の苦手候補は内部観察として残し、学習者が「観察中の候補も見たい」と明示した場合だけ表示する。

学習者が「違う」と判断したものは修正または削除する。

学習者が後から修正した場合は、修正後の内容を優先し、次回以降の復習とアドバイスに反映する。

### 17.2 苦手傾向の認定基準

Agentは、次のいずれかを満たす場合に、苦手傾向として認定する。

```md
1. 同じ苦手の種類、または近い苦手傾向タグが2回以上出ている
2. 同じ技術内容で「一部あいまい」または「要復習」が2回以上出ている
3. 同じ構造理解で、処理やデータの流れを追えない状態が2回以上出ている
4. 同じ思考プロセスで、原因仮説、設計判断、優先順位づけなどの誤りが2回以上出ている
```

1回だけの質問、初回の単発ミス、環境固有の一時的なエラーは、原則として苦手傾向として認定しない。

例:

```md
## Agent認定の苦手傾向
- 処理の流れを追う前に、個別コードへ意識が向きやすい
  - 種類: 構造理解
  - 根拠ログ: 2026-08-05/001-route-flow.md
  - 確信度: 中
  - 認定基準: 近い苦手傾向タグが2回以上出ている
  - 状態: Agent認定

## 修正済みの苦手傾向
- エラー文を読めないというより、原因仮説の優先順位づけが苦手
  - 種類: 思考プロセス
  - 学習者修正: 2026-08-09
  - 次回以降の扱い: error / 原因仮説

## 得意な進め方
- 先に全体像を確認してから、ファイルや関数を順番に見ると理解が進みやすい
  - 根拠ログ: 2026-08-06/002-controller-flow.md

## 学習スタイル
- 抽象的な説明だけでなく、実際のコード例と処理の流れを合わせると定着しやすい

## メンター時の注意点
- 最初から修正コードを出すより、確認順序を先に提示する
- 苦手傾向は基準に基づいてAgentが認定し、根拠と修正可能性を一緒に示す

## 成長している傾向
- RouteからControllerまでの流れを、自分の言葉で説明できる回数が増えている
```

## 18. メンター機能

### 18.1 機能範囲

メンター機能はProgrammingAIの価値の中心であるため、要件としてしっかり設計する。
メンター機能は、学習開始時の表示だけでなく、苦手分野の基本判定、復習、確認ポイントの提示まで扱う。

メンター機能の範囲は次の通りである。

- 学習者が「学習開始」と入力したときにメンター表示を行う
- 最近の学習傾向を簡単に表示する
- 復習を1件出題する
- 最初に意識する確認ポイントを1つ以上提示する
- 確定学習ログと日次学習傾向ファイルをもとに、参照できる範囲で軽く傾向を出す
- 確定学習ログから、苦手傾向の認定基準に当てはまる場合に苦手分野を基本判定する
- 苦手分野を `技術知識`、`構造理解`、`思考プロセス` のいずれかに分類して表示する
- 苦手分野に関係する技術領域を表示する
- 苦手分野の根拠ログを最大3件までリンクで表示する
- 学習開始時に表示する苦手分野は、確信度 `中` 以上のものだけに絞る
- 根拠が少ない場合は、苦手分野を断定せず「判断材料が少ない」と表示する

苦手分野の基本判定は、確定学習ログの件数だけでは判断しない。
17.2の「苦手傾向の認定基準」に当てはまる場合に判定する。
たとえば、同じ苦手の種類、近い苦手傾向タグ、同じ技術内容、同じ構造理解、同じ思考プロセスのつまずきが繰り返し確認できる場合に、苦手分野として扱う。

ただし、学習者に通常表示する苦手分野は、確信度 `中` 以上のものに限る。
確信度 `低` のものは、learner-profile.mdに内部観察として残し、今後同じ内容が繰り返された場合に表示候補へ上げる。

メンター機能は、実装チェックポイントを分けて検証する。
たとえば、ダミーの確定学習ログを使って、苦手分野の判定、確信度 `中` 以上の表示、根拠ログリンク、復習1件、最初に意識する確認ポイントが想定通り出るかを確認する。

### 18.2 学習開始時の出力

標準では、学習者が「学習開始」と入力したタイミング、または日付が変わった後の最初のプログラミング学習質問で、mentorサブAgentが学習開始時の提案を表示する。

この表示は、新規チャットだけに限定しない。
同じチャット内で日付が変わった場合や、前日の `current-term` が残っている場合でも、確認待ちで停止すべき状態でなければ日次mentor出力を行う。

設定により、起動時自動表示へ切り替え可能にする。

出力項目は次の3つとする。

```md
# 最近の学習傾向
# 復習
# 最初に意識する確認ポイント
```

学習ログがまだ少ない場合、mentorサブAgentは無理に学習傾向や苦手を断定しない。
根拠として使える確定学習ログや日次学習傾向ファイルが不足している場合は、次のように表示する。

```md
# 最近の学習傾向
まだ判断材料が少ないため、学習傾向は十分に判断できません。
今日の学習ログが増えると、次回以降に傾向を出しやすくなります。
```

この場合でも、利用できる範囲で復習候補や最初に意識する確認ポイントを提示してよい。
ただし、根拠が不足している内容を苦手傾向として断定してはならない。

`最初に意識する確認ポイント` には、確信度 `高` の苦手傾向を毎回反映するわけではない。

確信度 `高` の苦手傾向は、現在の質問内容または学習テーマと関連する場合だけ反映する。

関連する学習テーマかどうかは、次の4つを根拠に判断する。

```md
1. 質問分類
2. 技術領域
3. 苦手種類
4. 参照範囲
```

たとえば、質問分類が `feature`、技術領域が `Route / Controller`、苦手種類が `構造理解`、参照範囲が `routes/web.php` やControllerである場合、過去の「処理の流れを追うのが苦手」という苦手傾向と関連が高いと判断する。

4つの判断材料のうち2個以上が一致した場合に、関連する学習テーマと判断する。

参照範囲が明示されていない場合は、参照範囲は一致数に含めず、残りの情報から判断する。

毎回同じ苦手を表示すると学習者の負担が大きくなるため、現在の学習に関係する場面でのみ、確認ポイントとして提示する。

### 18.3 復習

復習は、次の候補からランダムで1件だけ出題する。

- 昨日できなかった箇所
- 3日前にできなかった箇所
- 7日前にできなかった箇所
- 10日前にできなかった箇所

ただし、苦手傾向に該当する内容を優先する。

苦手の種類では、`技術知識` と `構造理解` を優先する。

復習候補の優先順位は、次の順番で判断する。

```md
1. 技術知識または構造理解に該当する要復習ログ
2. 技術知識または構造理解に該当する一部あいまいログ
3. 思考プロセスに該当する要復習ログ
4. 思考プロセスに該当する一部あいまいログ
5. その他の復習候補
```

復習優先順位に入れるAgent認定の苦手傾向は、確信度 `高` または `中` のものに限る。

確信度 `低` の苦手傾向は、復習候補には含めず、今後の観察対象として残す。

同じ優先度の中に複数の復習候補がある場合は、次の順番で選ぶ。

```md
1. 要復習が付いているもの
2. 繰り返し出ている苦手
3. 直近の学習ログ
4. ランダム
```

「繰り返し出ている苦手」は、同じ苦手の種類、または近い苦手傾向タグが2回以上出ているものとする。

完全一致だけで判断せず、mentorサブAgentが学習ログの具体内容を見て、同じつまずきとして扱えるかを判断する。

この判定では、タグの文字列だけでなく、学習ログに書かれた「苦手の具体内容」「つまずきの中核」「次に同じ問題が出たら見る順番」を根拠として確認する。

近い苦手としてまとめた判断は、苦手認定基準を満たす場合、learner-profile.mdに `状態: Agent認定` として保存する。

4日に1回の「最近の学習傾向」表示時に、Agentが認定した苦手傾向とまとめ方を表示し、学習者が違うと感じた場合は修正できるようにする。

このとき表示する苦手傾向は、原則として確信度 `中` 以上のものに限る。
確信度 `低` の苦手候補は通常表示しない。

最近の学習傾向では、通常は確信度を表示しない。

学習者が「確信度も見たい」「判断の強さを確認したい」と伝えた場合のみ、確信度を表示する。
学習者が「観察中の候補も見たい」と伝えた場合のみ、確信度 `低` の苦手候補も表示してよい。

根拠になった学習ログは本文を長く転載せず、ローカルファイルへのMarkdownリンクとして表示する。

リンクをクリックすると、対応する確定学習ログを確認できるようにする。

根拠ログリンクの表示は最大3件までとする。

4件以上の根拠がある場合は、関連度が高いもの、繰り返しの判断に重要なもの、直近のもの、の順で最大3件だけ表示する。

### 18.4 復習の出題形式

復習は次の型で出力する。

```md
# 復習
# 復習対象
# Q. 出題内容

<details>
<summary>A. 確認する</summary>

答え・確認ポイントを記載する。

</details>

# 関連する過去のつまずき
```

### 18.5 復習回答後の評価

復習への回答後、mentorサブAgentは回答を軽く評価する。

評価は次の3段階とする。

- できた
- 一部あいまい
- 要復習

一部あいまい、または要復習の場合は、必要に応じて日次学習傾向ファイルへ反映する。

### 18.6 苦手傾向チェック

苦手傾向チェックは、4日に1回を初期値とし、設定で変更可能にする。

mentorサブAgentは、最近の学習傾向の中でAgent認定の苦手傾向を提示する。
提示対象は、通常は確信度 `中` 以上の苦手傾向に限る。
確信度 `低` の苦手候補は、内部観察として保持し、学習者が明示的に希望した場合だけ表示する。

同じタイミングで、learner-profile.mdに仮反映されている軽い観察もまとめて確認する。

同じタイミングで、Agentが「近い苦手」としてまとめた内容も表示し、学習者が修正できるようにする。

苦手傾向の提示形式は次の通りである。

```md
# 最近の学習傾向

## 見えてきた傾向
## 根拠
- [2026-08-05/001-route-flow.md](learning-logs/2026-08-05/001-route-flow.md)
- [2026-08-07/002-controller-role.md](learning-logs/2026-08-07/002-controller-role.md)
- [2026-08-09/001-data-flow.md](learning-logs/2026-08-09/001-data-flow.md)

## 仮反映したプロフィール情報
## 追加された技術領域
## 近い苦手としてまとめた候補
## Agent認定の苦手傾向
## 改善のための提案
## 確認
```

学習者が修正した場合、次回以降の復習やアドバイスでは修正後の内容を優先する。

## 19. 設定ファイル

設定値は、.codex/config.tomlで管理する。

設定キーは英語、説明コメントは日本語で記述する。

設定に関係するファイルは、次の4つに分ける。

```md
.codex/config.toml:
実際にAgentの動作へ適用する設定ファイル。
学習者が必要に応じて編集できる。

.codex/config.defaults.toml:
config-guardがチェック基準として使用するチェック定義ファイル。
必須キー、デフォルト値、値の型、許可された値、許可された範囲を定義する。
`.codex/config.toml` と同じ形の初期値一覧ではない。
原則として学習者は編集しない。

.codex/skills/config-defaults-provider/templates/config.toml:
.codex/config.toml を新規作成するときの元になるテンプレート。
実際のAgent動作を直接決める設定ではない。
原則として学習者は編集しない。

.codex/skills/config-defaults-provider/templates/config.defaults.toml:
.codex/config.defaults.toml を新規作成または復旧するときの元になるテンプレート。
実際のAgent動作を直接決める設定ではない。
必須キー、型、初期値、許可値、許可範囲を持つチェック定義のテンプレートである。
原則として学習者は編集しない。
```

config-guardは、`.codex/config.defaults.toml` を基準にして `.codex/config.toml` をチェックする。

`.codex/config.defaults.toml` は、`.codex/config.toml` と同じ形の初期値一覧ではなく、config-guardが読むチェック用の形式とする。

`.codex/config.defaults.toml` には、各設定キーごとに次の情報を持たせる。

```md
1. 設定キー名
2. 必須かどうか
3. 値の型
4. デフォルト値
5. 許可された値
6. 許可された範囲
7. 設定の説明
```

`.codex/config.defaults.toml` の具体的な書き方は、`[[settings]]` で設定ごとのチェック定義を並べる形式で固定する。

使用できる`type`は、次の5種類に固定する。

```md
string: 文字列
integer: 整数
boolean: 真偽値
string_array: 文字列の配列
table_array: テーブルの配列
```

基本形式は次の通りである。

```toml
[[settings]]
key = "confirmation_mode"
required = true
type = "string"
default = "strict_stop"
allowed_values = ["strict_stop", "agent_decides"]
description = "承認が必要な場面で、回答がない場合の動作"
```

数値範囲を持つ設定は、次のように記述する。

```toml
[[settings]]
key = "learning_profile_retention_days"
required = true
type = "integer"
default = 60
min = 1
max = 365
description = "日次学習傾向ファイルを保持する日数"
```

許可された値、または許可された範囲が不要な設定では、その項目は空で書かず、省略する。

config-guardは、`allowed_values`、`min`、`max` などのチェック項目が省略されている場合、その条件ではチェックしないものとして扱う。

省略された項目を、エラーや警告として扱わない。

例:

```toml
[[settings]]
key = "technical_area_custom_candidates"
required = true
type = "string_array"
default = []
description = "Agentが追加した技術領域"
```

`type = "string_array"` の場合、config-guardは値全体が配列であり、配列内の各要素が文字列であることを確認する。

配列内に文字列以外の値が含まれる場合は、エラーとして扱う。

この場合、Agentは通常の質問回答、分類、解説は継続するが、その設定を使う処理だけを停止する。

config-guardは、対象の設定キー、問題のある要素の位置、実際の値の型、修正案をメインAgentへ返す。

テーブル配列を持つ設定は、次のように記述する。

```toml
[[settings]]
key = "technical_area_aliases"
required = true
type = "table_array"
default = []
required_fields = ["from", "to"]
field_types = { from = "string", to = "string" }
description = "技術領域の読み替え設定"
```

`type = "table_array"` の場合、各要素に必要な項目は `required_fields` で定義する。

各項目の型は `field_types` で定義する。

config-guardは、`table_array` の各要素について、次の内容を確認する。

```md
1. 値全体がテーブル配列である
2. 各要素に required_fields の項目が存在する
3. required_fields の値が空ではない
4. field_types に定義された型と一致している
5. required_fields 以外の余分な項目があるか
```

`table_array` の各要素に `required_fields` 以外の余分な項目がある場合、エラーではなく警告として扱う。

余分な項目だけを理由に、通常の質問回答、分類、解説、または該当設定を使う処理は停止しない。

ただし、設定名のスペルミスや不要な項目の可能性があるため、config-guardは余分な項目名と警告箇所を表示する。

`required_fields` または `field_types` が不足している場合、`table_array` のチェック定義自体に問題があるものとして扱う。

`.codex/config.defaults.toml` はAgent側の基準ファイルであり、通常の設定変更では編集対象にしない。

`.codex/config.defaults.toml` を変更したい場合は、設定変更ではなくAgent設計変更として扱う。

その場合、Agentは変更理由、影響を受ける設定、既存の `.codex/config.toml` への影響を確認してから更新する。

`.codex/config.defaults.toml` が存在しない、または壊れていて読めない場合は、設定チェックを正常実行できない重大エラーとして扱う。

この場合、Agentは設定に依存する処理を停止する。

この場合、config-guardはconfig-defaults-providerを呼び出し、`.codex/config.defaults.toml` の初期内容を復旧用テンプレートとして取得する。

復旧用テンプレートは、学習者に提示する修正案としてのみ使用する。

Agentは、学習者が承認した場合だけ `.codex/config.defaults.toml` を作成または上書きする。

停止対象には、設定値を参照して動く処理を含める。

例:

```md
- 参照範囲モードの切り替え
- 確認待ち時の自動進行可否
- 学習ログ保持日数による自動削除
- 技術領域の読み替え分析
- メンター表示頻度の判定
```

通常の会話、要件定義の相談、基準ファイルの修復相談は継続してよい。

Agentは、`.codex/config.defaults.toml` のエラー内容を表示し、修復が必要であることを学習者へ伝える。

学習者が `.codex/config.toml` を直接編集できる設定では、メインAgentは使用前にconfig-guardを必ず呼び出し、設定ファイルの形式を確認する。

`.codex/config.toml` が存在しない場合、Agentはconfig-defaults-providerから初期内容を取得し、作成案として学習者へ提示する。

Agentは、学習者が承認した場合だけ `.codex/config.toml` を作成する。

`.codex/config.toml` が存在している場合、Agentは不足している必須キーだけを確認する。

必須キーが不足している場合、Agentはconfig-defaults-providerから該当キーの初期値を取得し、追記案として学習者へ提示する。

この場合、既存の設定値は上書きしない。

Agentは、学習者が承認した場合だけ不足キーを `.codex/config.toml` に追記する。

config-guardのチェック対象は、次の通りとする。

```md
1. TOMLとして読めるか
2. 必須キーがあるか
3. 値の型が正しいか
4. 許可された値、または許可された範囲内か
```

また、Agentが知らない設定キーが追加されている場合は、エラーではなく警告として表示する。

未知の設定キーは、Agentの動作を止める対象にはしない。

ただし、設定名のスペルミスや不要な設定の可能性があるため、Agentは警告箇所を表示する。

警告箇所には、可能な限り次の内容を含める。

```md
1. 設定キー名
2. 行番号
3. 設定ファイル内の場所
4. 警告理由
```

行番号を特定できない場合は、設定キー名と設定ファイル内の場所を表示する。

必須キーが存在しない場合、Agentはデフォルト値を使った修正案を提示する。

このとき使用するデフォルト値は、`.codex/config.defaults.toml` から取得する。

必須キー不足時の修正案には、次の内容を含める。

```md
1. 不足している設定キー
2. 追記するデフォルト値
3. その設定が必要な理由
4. 追記予定の場所
```

Agentは、学習者が承認した場合だけ `.codex/config.toml` に必須キーを追記する。

学習者が承認しない場合は、学習者がchatで修正内容を入力し、Agentはその内容を反映して再チェックする。

値の型とは、文字列、数値、配列、真偽値など、設定ごとに期待されるデータ形式である。

許可された値とは、`strict_stop` や `agent_decides` のように、設定として選べる値が決まっているものを指す。

許可された範囲とは、保持日数や表示間隔のように、数値として使える上限、下限が決まっているものを指す。

形式エラーがある場合、Agentは通常の質問回答、分類、解説は継続する。

ただし、形式エラーがある設定値を使う分析や処理だけを停止する。

config-guardは、形式エラーの内容、影響を受ける設定キー、停止する処理、継続できる処理、修正案をメインAgentへ返す。

設定エラー時の修正フローは、次の通りとする。

```md
1. Agentがエラー内容を表示する
2. Agentが修正案を提示する
3. Agentが「この修正案で修正してよいですか？」と確認する
4. 学習者が承認した場合、Agentが `.codex/config.toml` を修正する
5. 学習者が承認しない場合、学習者がchatで修正内容を入力する
6. Agentが修正内容を反映する
7. Agentが再チェックする
```

Agentは、学習者の承認なしに `.codex/config.toml` を自動修正しない。

```toml
# .codex/config.tomlの形式チェック
config_validation = "enabled"

# .codex/config.tomlのチェック対象
config_validation_check_items = ["toml_parse", "required_keys", "value_types", "allowed_values_and_ranges", "unknown_keys"]

# .codex/config.tomlが存在しない場合の扱い
# propose_initial_config_on_approval: 初期内容を提示し、承認された場合だけ作成する
missing_config_file_policy = "propose_initial_config_on_approval"

# .codex/config.tomlの初期値提供元
# config-defaults-provider: 共通Skillから初期内容を取得する
config_initial_value_source_skill = "config-defaults-provider"

# config-defaults-provider内テンプレートの編集方針
# agent_design_only: 通常編集せず、Agent設計変更時だけ更新する
config_template_edit_policy = "agent_design_only"

# .codex/config.tomlが存在している場合の初期値反映方針
# append_missing_keys_only_on_approval: 既存値は上書きせず、不足している必須キーだけ承認後に追記する
existing_config_initial_value_policy = "append_missing_keys_only_on_approval"

# .codex/config.defaults.tomlの編集方針
# agent_design_only: 通常の設定変更では編集せず、Agent設計変更時だけ更新する
config_defaults_edit_policy = "agent_design_only"

# .codex/config.defaults.tomlの内容形式
# validation_schema: config.tomlと同じ形ではなく、必須キー・型・初期値・許可値・範囲を持つチェック定義として扱う
config_defaults_content_format = "validation_schema"

# .codex/config.defaults.tomlの設定定義形式
# settings_array: [[settings]]で設定ごとのチェック定義を並べる
config_defaults_schema_format = "settings_array"

# .codex/config.defaults.tomlで使用できる型
config_defaults_allowed_types = ["string", "integer", "boolean", "string_array", "table_array"]

# table_arrayの項目チェック方式
# required_fields_and_field_types: required_fieldsで必須項目、field_typesで各項目の型を定義する
config_defaults_table_array_schema_policy = "required_fields_and_field_types"

# table_array内の余分な項目の扱い
# warn: エラーにはせず、余分な項目名と警告箇所を表示する
table_array_extra_field_policy = "warn"

# string_array内に文字列以外が含まれる場合の扱い
# error_skip_affected_feature: エラーとして扱い、その設定を使う処理だけ止める
string_array_invalid_item_policy = "error_skip_affected_feature"

# 不要なチェック項目の扱い
# omit_optional_constraints: allowed_values、min、maxなど不要な項目は省略し、省略時はその条件でチェックしない
config_defaults_optional_constraint_policy = "omit_optional_constraints"

# .codex/config.defaults.tomlの初期値提供元
# config-defaults-provider: 共通Skillから初期内容と復旧テンプレートを取得する
config_defaults_source_skill = "config-defaults-provider"

# .codex/config.defaults.tomlが存在しない、または壊れている場合の復旧方針
# propose_template_restore_on_approval: 復旧テンプレートを提示し、承認された場合だけ作成または上書きする
config_defaults_recovery_policy = "propose_template_restore_on_approval"

# 未知の設定キーの扱い
# warn: エラーにはせず、警告箇所を表示する
# error: エラーとして扱う
```

## 20. 実装チェックポイント一覧

### 20.1 分類サブAgent + classifier Skill

対象は、分類サブAgentと `.codex/skills/classifier/SKILL.md` である。

目的は、学習者の質問を `feature`、`unit`、`assess`、`error` のいずれかへ安定して分類できるか確認することである。

ダミー入力は、8.6のclassifier Skillのダミー検証を使用する。

期待する出力は次の通りである。

- `classification` が期待分類と一致する
- `reason` が1〜2文で短く説明される
- `confidence` が `high`、`medium`、`low` のいずれかで返る
- `missing_info` が必要な場合だけ返る
- `need_user_confirmation` が適切に返る
- 軽微な不足情報の場合は、`assumption` が返る

作成または更新されるファイルはない。
このチェックポイントは、分類の挙動確認であり、学習ログやプロフィールは更新しない。

合格条件は、8.6の8件すべてで期待分類、分類理由、不足情報、確認要否が要件通りに出ることである。

不合格だった場合は、次の要件箇所を見直す。

- 5.2 分類サブAgent
- 8. 質問分類
- 8.5 classifier Skill
- 8.6 classifier Skillのダミー検証

### 20.2 featureサブAgent + feature-answer Skill

対象は、featureサブAgentと `.codex/skills/feature-answer/SKILL.md` である。

目的は、機能全体、複数ファイルのつながり、処理の流れ、データの流れを、参照済み情報に基づいて説明できるか確認することである。

ダミー入力は、9.3のfeature-answer Skillのダミー検証を使用する。

期待する出力は次の通りである。

- 9.1の共通テンプレートに沿って回答する
- `理解ステップ` で、ファイルの役割、処理の起点、処理の受け渡し、データの流れ、終点を説明する
- 参照済み情報と未確認情報を分ける
- 未確認のRoute、Controller、DB保存処理などを断定しない
- 必要な場合は、追加で確認したい参照範囲と理由を提示する
- 最後に軽い理解確認を1つ出す
- 管理情報の更新案として、理解度候補、苦手の具体内容候補、苦手傾向タグ候補、学習ログ化候補を返す

作成または更新されるファイルはない。
このチェックポイントは、feature回答の挙動確認であり、学習ログやプロフィールは更新しない。

合格条件は、9.3の5件すべてで、参照済み情報と未確認情報を分けたうえで、学習者が次に見る順番を使える回答になっていることである。

不合格だった場合は、次の要件箇所を見直す。

- 5.3 featureサブAgent
- 9.1 共通テンプレート
- 9.2 feature-answer Skill
- 9.3 feature-answer Skillのダミー検証

### 20.3 unitサブAgent + unit-answer Skill

対象は、unitサブAgentと `.codex/skills/unit-answer/SKILL.md` である。

目的は、コード一文、関数、メソッド、API、構文を、学習者が自力で読める単位まで分解して説明できるか確認することである。

ダミー入力は次の通りである。

```md
1. 「$user->books()->create($data) の意味が分かりません」
期待値: オブジェクト、リレーション、create、引数、保存結果に分解して説明する。

2. 「document.getElementById('isbn').value.trim() が分かりません」
期待値: 要素取得、値の取得、空白除去を順に説明する。

3. 「return redirect()->route('books.index') の意味は何ですか」
期待値: redirect、route名、画面遷移の関係を説明する。
```

合格条件は、コードを丸暗記させず、部品ごとの役割、実行順序、他でも使える考え方、次に見る順番を出せることである。
不合格の場合は、unit-answer Skillの分解手順と出力形式を修正し、同じダミー入力で再検証する。

### 20.4 assessサブAgent + assess-answer Skill

対象は、assessサブAgentと `.codex/skills/assess-answer/SKILL.md` である。

目的は、学習者のコード、説明、設計、テスト、理解内容を、正誤だけでなく改善点と次の学習につながる形で評価できるか確認することである。

ダミー入力は次の通りである。

```md
1. 「このバリデーションの書き方で問題ありませんか」
期待値: 良い点、問題点、改善案、実務上の注意を分けて返す。

2. 「私の理解では、RouteはControllerを呼び出す場所です。合っていますか」
期待値: 合っている部分と不足している部分を分けて評価する。

3. 「このテスト内容で十分ですか」
期待値: テスト観点の不足、追加すべき確認、過不足を整理する。
```

合格条件は、学習者を否定するだけでなく、現在の理解段階と次の改善点を明確にすることである。
不合格の場合は、assess-answer Skillの評価軸、改善案、理解ステップを修正し、同じダミー入力で再検証する。

### 20.5 errorサブAgent + error-answer Skill

対象は、errorサブAgentと `.codex/skills/error-answer/SKILL.md` である。

目的は、エラー文、実行状況、提示コードから、原因を断定せず、意味、場所、原因仮説、確認順序、修正案、検証方法を整理できるか確認することである。

ダミー入力は次の通りである。

```md
1. 「Call to undefined method App\Models\User::books() が出ます」
期待値: リレーション未定義、メソッド名違い、Model確認の順に仮説を出す。

2. 「404 Not Found になります」
期待値: URL、Route、HTTPメソッド、Controller、キャッシュの順に確認する。

3. 「SQLSTATE[42S02]: Base table or view not found が出ます」
期待値: テーブル未作成、migration未実行、テーブル名違いを仮説として整理する。
```

合格条件は、修正コードを最初に出さず、確認順序を先に提示し、修正後の検証方法まで出すことである。
不合格の場合は、error-answer Skillの原因仮説、確認順序、修正案の出し方を修正し、同じダミー入力で再検証する。

### 20.6 mentorサブAgent + mentor Skill

対象は、mentorサブAgentと `.codex/skills/mentor/SKILL.md` である。

目的は、確定学習ログ、日次学習傾向ファイル、learner-profile.mdから、最近の学習傾向、復習1件、最初に意識する確認ポイントを提示できるか確認することである。

ダミー入力は次の通りである。

```md
1. Route / Controller / Blade の流れで2回つまずいた確定学習ログ
期待値: 構造理解の苦手として通常表示の対象にする。確信度の値そのものは通常表示しない。

2. fetchの単発質問だけが1件ある状態
期待値: 苦手とは断定せず、判断材料が少ないと表示する。

3. 技術知識と構造理解の候補が両方ある状態
期待値: 技術知識 / 構造理解を優先し、復習候補を1件だけ出す。
```

合格条件は、確信度 `中` 以上の候補だけを通常表示対象にし、確信度の値そのものは通常表示せず、根拠ログリンクを最大3件まで出し、学習者が修正できる形で提示することである。
不合格の場合は、mentor Skillの苦手判定、確信度、復習選定、表示形式を修正し、同じダミー入力で再検証する。

ダミー入力と期待値は次の通りである。

```md
1. config.tomlに必須キーが不足している
期待値: config-guardが警告またはエラーを出し、デフォルト値を使った修正案を提示する。

期待値: Agent判断の軽量メモだけを日次学習傾向へ保存する。
```

対象は、メインAgent、全サブAgent、全Skill、学習ターム管理、学習ログ生成、メンター表示である。

目的は、個別に合格したサブAgentとSkillをつなぎ、ProgrammingAIとして一連の学習支援フローが動作するか確認することである。

ダミー入力は次の通りである。

```md
1. 学習者がfeature質問を入力する
2. classifierがfeatureへ分類する
3. scope-readerが参照範囲を確認する
4. feature-answerが回答を作る
5. メインAgentが理解確認を出す
6. 学習者が理解確認に答える
7. learning-term-managerがターム終了候補を判断する
8. learning-log-workflowがログ化するか確認する
9. 学習者が「内容をまとめてほしい」と依頼する
10. learning-log-workflowがログ候補を提示する
11. 学習者が保存を許可する
12. 確定学習ログとNotion貼り付け用ドラフトを生成する
13. profile-memoryが必要な軽量メモまたは更新案を作る
14. mentorが学習開始時に最近の傾向、復習、確認ポイントを表示する
```

合格条件は、各工程で期待した分類、回答、確認、保存候補、メンター表示が出ることである。
どれか1つでも期待値から外れた場合は統合チェックを不合格とし、該当するサブAgentまたはSkillへ戻って修正し、再度統合チェックを行う。
統合チェックが合格するまで、実運用に進まない。

### 21.4 開発タスクへの分解方針

開発では、次の順番で実装する。

1. `.codex/config.toml` と `.codex/config.defaults.toml` の設定読み込み
2. `config-guard` による設定検証
3. `scope-reader` による参照範囲確認
4. `classifier` による質問分類
5. `feature / unit / assess / error` の回答生成
6. `learning-term-manager` による学習ターム作成、状態管理、自動採番
7. `learning-log-workflow` によるターム境界判定、ログ候補、保存許可、確定ログ、Notionドラフト、軽量メモ生成
8. `profile-memory` による日次学習傾向とlearner-profile更新候補
9. `mentor` による最近の学習傾向、復習1件、確認ポイントの提示
10. `SMOKE_TEST.md` と `.codex/internal/scripts/run_all_checks.rb` による回帰確認

各実装タスクでは、対応する検証ハーネスを実行し、期待値が出るまで次へ進まない。

### 21.5 開発中に調整してよい内容

次の内容は、実装中に必要に応じて調整してよい。

- 内部関数名
- ファイル生成処理の細かな実装方法
- エラー表示文の細かな表現
- テストスクリプトの分割方法
- READMEの説明順序

ただし、次の内容を変更する場合は、要件変更として扱う。

- 学習者が明示した範囲だけを参照する方針
- ログ候補と保存許可を分ける方針
- 保存拒否時に軽量メモを残さない方針
- Notionへ自動保存しない方針
- サブAgentが直接ファイル更新しない方針
- 苦手傾向の認定基準
- 確信度の値そのものを通常表示しない方針
